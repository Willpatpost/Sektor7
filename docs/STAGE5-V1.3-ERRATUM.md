## E1 — Correct durable-transition recovery and supersession (corrects §5.5.2)

v1.3's recovery rule ("apply iff the ids are unfinished and the episode matches; a later record supersedes earlier unapplied ones") is wrong in two ways. Corrected:

**Recovery classifies each durable transaction against the recovered state into exactly three cases:**

- **Pre-state** — the transition exists in the journal and was **not applied**: the plan's source preconditions verify (every plan obligation id is unfinished and located where the plan expects — queued/blocked, not held; the region's episode equals the plan's source episode; the world scratch still holds the signals the plan captures). → **Apply the plan.**
- **Post-state** — the transition **was already applied** and the recovered state matches the plan's **expected result**: every plan obligation id is **held** (or consumed by later valid history), the region's episode has **advanced to the plan's target** (source+1 or beyond via later applied transitions), the checkpoint — where retained — matches the plan's checkpoint digest, and the captured keys are present in the ledger/journal state. → **Treat as completed; no duplicate application.** A post-state **must not be rejected merely because its episode is no longer equal to the plan's source episode** — advanced episode metadata and suspended obligations are the *signature* of a correctly applied transition.
- **Incompatible** — neither pre-state nor post-state verifies. → **Fail closed and preserve evidence** (governed resolution), unless an explicit durable cancellation covers the transaction (below).

**Supersession is causal, not positional.** A higher journal sequence does **not** authorize superseding an earlier unapplied transition. Recovery processes a region's journal transactions **in journal-sequence order**, applying or recognizing each in turn; a later transition is valid only if it is **causally consistent with the earlier transition already having been applied** (episodes advance only on durable commit *and* application, so encountering source-episode E+1 during in-order replay is reachable only after E was applied or explicitly canceled). The **only** authorized skip of an unapplied durable intent is an **explicit durable `CancellationRecord`** (journal-sequence ordered; references the canceled transaction id; reason-coded) — an equally durable cancellation/supersession protocol. If replay reaches a transition whose predecessor is neither applied nor canceled, **that is itself evidence of divergence: fail closed, preserve evidence** — never archive an unapplied transition merely because a later record exists.

**Consequence preservation:** pre-state application applies the keyed deltas exactly-once (applied-key reconciliation); post-state recognition never re-applies; incompatible-and-uncanceled never silently drops. No window loses or duplicates a consequential capture.

## E2 — The actual all-or-nothing live mutation boundary (corrects §5.5.2)

`Spine::suspend_ids()` being batched does **not** by itself make the multi-object mutation atomic. The mechanism is a **staged commit bundle** with a strict prepare/install discipline:

- **`prepare` — every fallible or potentially failing step, and every precondition, before any authoritative mutation.** From read-only sources, `prepare` constructs **off-stage** the complete replacement state for *every* affected object: the held `Pending` records (from the plan's full obligation identities — no further spine reads needed at install), the `RegionCheckpoint` (complete contents), the CaptureLedger entries (keys + deltas), the replacement `RegionState` (episode advanced, level, checkpoint), and the world's post-transition scratch state (signals cleared, sentinels set, region LOD updated). It then **re-validates every precondition immediately before installation** (ids present in expected locations, none executed, ledger key-status, episode equality). A failure here aborts **before any mutation** — the coherent pre-state stands.
- **`install` — non-fallible by construction.** Because every structure was fully built during `prepare`, installation consists only of: removals of the enumerated ids from the queues/blocked (non-allocating), insertions of the **pre-built** values into `held`/`held_index`/the ledger/the regional state (moves of already-constructed values; the only allocation involved is BTreeMap/BTreeSet node allocation, which under Rust's failure model **aborts the process rather than returning a recoverable error**), and pre-allocated writes/swaps. **There is no code path that installs part of the transition and returns `Err`** — no recoverable error can leave a partial installation.
- **No partial state is ever observable.** Install runs inside the tick boundary on the single-threaded engine: no simulation step executes between install steps, and snapshots/saves never run mid-transition (quiescent-point discipline). A crash *during* install kills the process — the partially-installed in-memory state dies with it and is **unobservable**: recovery reconstructs from the last anchor + journal and classifies the transaction per §E1 (pre-state → apply; a later anchor that captured the completed install → post-state). **Recovery from a process crash at any stage is idempotent** by §E1's rules.
- **The clock rule:** the boundary completes `prepare → journal → verify → install` (or aborts pre-durably, or halts fail-closed on a post-durable precondition/bug detection — the durable intent then stands for §E1 recovery or governed resolution). **A failure after a durable intent can never cause the clock to advance through an inconsistent transition** — the tick advances only past a completed installation.

The atomicity claim rests on this construction — fallible work isolated in `prepare`, non-fallible installation, unobservable intermediate states — not on any single batched method.

## E3 — Compaction representation: complement-of-unfinished (corrects §5.6/§5.6.1/§5.6.2)

**The observation (review):** the Spine allocates ids densely and successful obligations are never canceled, so at every stable boundary each allocated id belongs to exactly one of **Executed / Queued / Blocked / Held**. Therefore `executed == [0, next_seq) \ unfinished`, where the unfinished set is already materialized as the live queues, blocked map, and held map.

**Comparison across the review's dimensions:**

| Dimension | Executed bitset (v1.3) | **Complement-of-unfinished (selected)** |
|---|---|---|
| Long-campaign memory growth | Grows **1 bit per ever-allocated id, for the campaign's lifetime** — 12.5 MB per 100 M events, unbounded; compaction does *not* bound storage independently of lifetime event allocation | **Zero growth with history**: an unfinished-id index (maintained at the two allocation/execution sites) bounded by **live obligation count** (~thousands; scales with active work, not past) — plus the already-required queues/blocked/held |
| Membership-query complexity | O(1) | O(log u), u = unfinished count (~10 comparisons at u≈1,000) — negligible at every call site (`unmet_dependencies`, `is_executed`, ExecCtx checks) |
| Queues/blocked/held | Unaffected | The index changes only at allocation (insert) and execution (remove); suspension/blocking/unblocking do not change unfinished-ness — two maintenance sites |
| Causal dependencies on executed events | Exact | **Exact and identical**: a dep on an executed id resolves executed (id < next_seq ∧ not unfinished); a dep on a queued/blocked/held id correctly blocks |
| Future cancellation semantics | Survives a cancellation lifecycle naturally | **Bakes in the no-cancellation invariant** — validated structurally by the existing conservation gate (`scheduled == executed + queued + blocked + held` becomes the derivation's own check). A future cancellation lifecycle is out of every ratified scope; if it ever arrives, the representation changes under an explicit versioned-domain bump |
| Reconstruction/conservation invariants | Popcount/count gates | **Conservation becomes structural**: `stats.executed == next_seq − unfinished_count` is the single derivation check |
| Representation compatibility / deterministic continuation | New bitset section in compacted saves | **No executed section in compacted saves at all** (the unfinished structures are already serialized); the compacted domain hashes an unfinished-index digest; behavioral equivalence proven by continuation-invisibility tests — and the swap is **fingerprint-invisible in the live spine** (the executed set was never hashed by any Stage 0–4 domain, verified) |

**Selection [justified]:** the **complement-of-unfinished** representation, for both the live spine and compacted saves. It eliminates the lifetime-growing structure entirely; its costs (O(log u) membership, the no-cancellation precondition) are negligible and gated. **Resulting growth model (stated per the review):** nothing in the persisted or in-memory representation grows with lifetime event allocation except fixed-size counters (`next_seq`, Stats) — confirmed revision records are bounded by milestone rate + retention, anchors by cadence + retention, the unfinished index by live work, prefix summaries by compaction count + retention. The v1.3 implication that the bitset-era design bounded storage independently of lifetime allocation is **removed**; under the selected representation the bound is genuine. The live spine's `executed: BTreeSet<u64>` is replaced by the unfinished index with continuation-invisibility proofs and mechanically preserved historical fingerprints.

## E4 — Windows durability candidate/evidence classification (corrects §5.3.3)

- **The platform-specific directory-flush module is reclassified as UNPROVEN.** Microsoft documents `FILE_FLAG_BACKUP_SEMANTICS` for *obtaining* directory handles; that alone does **not** establish that `FlushFileBuffers` on such a handle provides the rename-metadata durability this contract requires. It remains a candidate hypothesis until authoritative documentation or a defensible implementation establishes the guarantee — no claim is made from it.
- **SQLite is evaluated as the preferred production fallback**, with the distinction the review set: **canonical save bytes and revision-chain semantics remain ours regardless of the local transactional storage implementation.** If SQLite is selected: suitable durability settings — **WAL with `synchronous=FULL`** where appropriate (FULL fsyncs on every commit — the abrupt-failure/power-loss-safe setting; NORMAL trades durability for speed and does not meet the contract) — and **every object required for an acknowledged canonical revision inside one transactionally consistent durability boundary**: the revision records, referenced snapshots/blobs, and the HEAD equivalent stored as in-database objects committed in the same transaction, because **making HEAD durable inside SQLite does not make separately stored, unsynchronized external blobs durable**. Chain bytes export/import unchanged for portability.
- The requirement stands unchanged: **Windows standalone-canonical confirmation must have a justified durability contract covering abrupt OS failure and power loss before production acceptance.** Provider selection remains reserved for the lead after the alternatives are properly evaluated (evidence: for SQLite — its documented WAL/FULL semantics, the bundled-build audit on CI/Windows/macOS, and the B2 obligations behind the unchanged trait; for the platform module — the missing authoritative flush documentation or a defensible verified implementation).

## E5 — Safe orphan reconciliation and cleanup (corrects §5.3.3's orphan paragraph)

A hash-failing object is **not automatically an orphan** — it may be corrupted canonical evidence referenced by the current HEAD or an earlier confirmed revision. Corrected rules, before any deletion or rewrite of a mismatching content-addressed object:

1. **Reference check:** walk the authoritative and recoverable history (the chain from HEAD, plus retained/recoverable anchors) — does any record reference this object's expected identity?
2. **If referenced → fail closed and preserve the evidence** (the §5.4 corrupt-history case governs — never deletion).
3. **If unreferenced → classify:** a genuinely incomplete write (a `create_new` object from a failed/interrupted preparation, with no commit record and no journal transaction referencing it) vs. a potentially important unacknowledged/ambiguous operation (an object whose write may have been part of an in-flight commit whose outcome is unknown).
4. **Quarantine, never auto-delete:** questionable objects are moved to a quarantine area (bytes, original name, and metadata preserved) and surfaced in diagnostics.
5. **Reconcile before permanent reclamation:** pending commit attempts and journal transaction identities are reconciled per §E1 **before** any quarantined object is permanently reclaimed. **Garbage collection never destroys the only surviving evidence of an ambiguous or lost acknowledged revision.**
6. **The retry-rewrite path** applies only after the reference check confirms unreferenced **and** the journal reconciliation confirms the transaction never became durable or acknowledged — and even then the superseded bytes go to quarantine first.
