## 0. Executive summary

Three production gaps stand between the accepted Stage 5 implementation and production persistence, each with a design answer in this document:

1. **The Windows durability boundary** [RATIFIED, v1.8 §5.3.1/§5.3.3-E4]: the custom `LocalFileMedium` on Windows carries `SyncTier::ProcessCrashOnly` from std — the N−1-valid/N-lost scenario (an acknowledged HEAD rename absent after OS crash/power loss while the previous chain stays valid and the loss is invisible to chain validation) is possible and unclaimed-against. The v1.8's own rule: "the Windows local medium is not fully accepted for production standalone campaigns until a justified abrupt-power-loss durability contract exists." **The design recommends the unified cross-platform SQLite-backed canonical medium (WAL + `synchronous=FULL`) behind the unchanged `CanonicalMedium` trait** (§2–§3) — the option the v1.8 already named "the preferred production fallback," now made concrete.
2. **Lifetime growth in two dimensions** [MEASURED, the B5 sweep]: the spine's execution ledger (~31.0 B serialized per execution) grows inside every session snapshot, and the canonical chain/journal/snapshots grow without a retention protocol. **The design makes the ratified v1.8 §5.6 compaction architecture concrete as the versioned `spine-history/2` form plus the checkpoint/rotation/verify-before-reclaim retention protocol** (§4), with the confirmed-evidence retention rule preserved as ratified and the bounded-total-storage question answered honestly (§4.3).
3. **Calling-thread persistence costs that grow with campaign duration** [MEASURED]: the serialization ~12.076 ms (dev) at the 4,800-tick / 3,492,240 B snapshot, past every frame budget at long durations. **The design proposes the single-writer-thread I/O orchestration** (§5) — capture on the authority thread (bounded by compaction), background publication through the one serialization point that also carries the confirmations (§5.2's ordering protocol).

The stage-gated implementation plan (§8, PP-B1..PP-B4) proposes four independently testable batches. **None is executed or authorized by this document.**

## 2. The storage-provider decision (objective 1)

### 2.1 The ratified starting position [RATIFIED]

The v1.8 §2.1 (Correction A) ratified: the custom file-backed medium with std OS-managed locking, **conditional on Batch 2 demonstrating correctness** — which it did (the B2 fault-injection matrix, competing processes, real child-process kills; CLOSED-PASS at `e36b122`). The v1.8 §5.3.3-E4 named the known candidate gap exactly: **Windows directory-metadata durability** — and named SQLite "the preferred production fallback" with three requirements this design adopts verbatim: (1) canonical save bytes and revision-chain semantics remain ours (SQLite is the transactional/durability layer, never the format); (2) WAL with `synchronous=FULL` (FULL fsyncs on every commit — the abrupt-power-loss-safe setting; NORMAL does not meet the contract); (3) **every object required for an acknowledged canonical revision inside one transactionally consistent durability boundary** — the revision records, referenced snapshots/blobs, and the HEAD equivalent committed in the same transaction, because making HEAD durable inside SQLite does not make separately stored external blobs durable.

**The gate has now fired.** The Stage 5 acceptance is complete (B1–B5 CLOSED-PASS; the physical rig run passed at `047faf9`), and the Windows boundary stands exactly as documented: std cannot establish the power-loss/OS-crash acknowledged-revision tier on Windows (a read-only directory handle cannot `sync_all`; opening a directory for write requires platform-specific creation flags — v1.8 §5.3.1). The production question the v1.8 reserved "for the lead at the B2 gate" is now before the lead, with all the evidence the v1.8 asked for.

### 2.2 The three options

**Option A — keep the custom medium everywhere (accept the Windows tier).** Rejected for production: it contradicts the v1.8's own rule ("not fully accepted for production standalone campaigns until a justified abrupt-power-loss durability contract exists"). Development use remains fully supported — the `LocalFileMedium` is retained permanently as the reference implementation and test oracle (§6.3).

**Option B — the narrow Windows-specific durability module.** Open the campaign directory with `FILE_FLAG_BACKUP_SEMANTICS` + write access (not expressible through std; requires a Win32 binding dependency) and issue `FlushFileBuffers` on the directory handle around the HEAD rename; or `MoveFileExW(MOVEFILE_WRITE_THROUGH)` for the rename itself. **Unproven per the v1.8's own evidence standard [RATIFIED, §5.3.3-E4]:** Microsoft documents the flag for obtaining directory handles and documents `FlushFileBuffers` for file data, but does not document that flushing a directory handle establishes rename-metadata durability; the candidate was explicitly ruled "unproven until authoritative documentation or a defensible implementation establishes the guarantee — no claim is made from it." No authoritative documentation has surfaced. Even if proven, the costs: the engine's first platform-specific unsafe code, a Windows-only divergence in the durability story (two mediums to qualify, two failure models to test), and a power-loss claim that cannot be demonstrated on available hardware (the testing-honesty rule — process-kill tests verify the process-crash tier only). **Rejected as the primary recommendation; documented as the fallback-of-the-fallback** (it remains the zero-new-dependency option if the owner rejects SQLite — with the explicit consequence that the Windows power-loss claim rests on an unproven platform behavior).

**Option C — the SQLite-backed canonical medium (WAL + `synchronous=FULL`).** The documented semantics: in WAL mode with `synchronous=FULL`, the WAL is fsynced at every commit — acknowledged-transaction persistence across process crash, OS crash, and power loss per SQLite's documented contract, on all three target platforms. Decades of deployment; battle-tested crash recovery (the WAL replay); atomic multi-statement transactions (one BEGIN…COMMIT installs records + objects + HEAD together — the nine-step CAS's external coordination becomes SQLite's internal commit protocol); internal cross-platform locking; mature observability/repair tooling (the `sqlite3` CLI). Costs, honestly: a new native dependency (the bundled C amalgamation compiled via `cc` — an additional native build path on CI, Windows, and the macOS port; the SDL3/cmake lesson is the precedent that native build paths are a real maintenance cost, though `rusqlite` bundled is a single well-known crate, materially simpler than the SDL path); ~1–1.5 MB embedded runtime; page-level I/O we do not strictly need; the WAL/`-shm` sidecar files (managed by §3.5's checkpoint policy); backup discipline (§6.2 — a live WAL-mode DB is not safely file-copied without a checkpoint, and the campaign backup spans the separate journal file).

## 3. The SQLite canonical medium — the detailed design [PROPOSED — D-PP-1]

### 3.1 The schema

One database file per campaign (e.g., `<campaign>/store.db` alongside the existing journal file — the campaign directory layout otherwise unchanged). Valid SQLite DDL:

```sql
CREATE TABLE meta (
  key   TEXT PRIMARY KEY,
  value BLOB NOT NULL
);
-- rows: 'head' (the 32-byte record hash, or empty for unfounded);
--       'authority' (the founding record's mode + campaign-id digest,
--                    set once at founding, never updated);
--       'provenance' (the migration marker, §6.1)

CREATE TABLE objects (
  hash   BLOB PRIMARY KEY,   -- SHA-256(bytes); 32 bytes enforced by the insert path
  domain TEXT NOT NULL,
  bytes  BLOB NOT NULL
);

CREATE TABLE records (
  hash   BLOB PRIMARY KEY,   -- SHA-256(bytes) — the canonical revision-record/1 bytes
  bytes  BLOB NOT NULL,      -- ARE the record; the lookup columns below are
  epoch  INTEGER NOT NULL,   -- derived from the decoded record at insert
  parent BLOB,
  idem   BLOB,
  kind   INTEGER NOT NULL,
  tick   INTEGER NOT NULL
);

CREATE UNIQUE INDEX records_idem_unique
  ON records(idem) WHERE idem IS NOT NULL;   -- the chain-wide idempotency-key uniqueness,
                                             -- enforced by the database itself
CREATE INDEX records_parent ON records(parent);
CREATE INDEX records_epoch  ON records(epoch);
```

(SQLite enforces no BLOB length in DDL — the `(32)` shape is enforced by the insert path; `records_idem_unique` is a partial unique index, valid SQLite DDL, excluding the founding record's NULL key.)

**Canonical-byte preservation:** the `bytes` columns carry the exact canonical encodings verbatim — the content hashes are the same SHA-256 values the file medium computes; a migrated store's `ChainSummary` (head, height, founding, records, content_objects) must be identical (§6.1's equivalence gate). SQLite is the transactional/durability layer, never the format — the v1.8's requirement (1).

### 3.2 The append — one transaction, one linearization, a complete outcome contract

**The operation sequence.** `BEGIN IMMEDIATE` → read `meta.head` **under the transaction** → compare with the caller's expected parent (a mismatch observed here is a genuinely changed authoritative parent, verified by a committed read → `ROLLBACK` → `RejectedStaleParent { observed }`) → `INSERT OR IGNORE` every `StoredObject` (content-addressed idempotence: an existing row is re-verified — its stored bytes must hash to the same identity; a mismatch is the referenced-corruption fail-closed case) → insert the record row → update `meta.head` → `COMMIT`.

**The linearization and acceptance boundary [the review's Finding-1 correction]: the successful `COMMIT` of the transaction containing the `meta.head` update.** The uncommitted HEAD update is invisible to every other connection (SQLite's documented isolation); `Accepted { id, tier }` is returned only after `COMMIT` returns success. There is no window in which an uncommitted HEAD update is observable as authoritative.

**`SQLITE_BUSY` is contention, never evidence of a stale parent [Finding-1 correction].** Policy: a bounded internal retry with backoff, within a configured busy timeout. Expiry → the operation aborts with the **typed contention error** (nothing began, nothing installed — a clean retryable abort, never `Unknown`, never stale). **`RejectedStaleParent` is returned only after a committed read shows `meta.head` ≠ the expected parent.** In WAL mode readers never block the writer — BUSY arises only from writer-writer contention.

**Concurrent-writer examples:**
1. *Two publishers, the same expected parent N:* both `BEGIN IMMEDIATE`; SQLite admits exactly one; the other retries. The winner commits head = N+1. The loser, admitted next, reads head = N+1 ≠ N under its transaction → `ROLLBACK` → `RejectedStaleParent { observed: N+1 }`. The stale verdict always follows a committed read of a genuinely changed parent.
2. *A foreign long-lived write transaction (e.g., a migration tool) holds the write lock past the timeout:* the publisher's BUSY retries expire → the typed contention abort; nothing installed; nothing reported stale. The session's next operation re-reads the true head.
3. *A writer dies mid-transaction:* SQLite's rollback-on-recovery discards the uncommitted transaction; the next opener reads the committed head. The dead writer's outcome for its caller is `Unknown` → `reconcile_unknown`.

**`reconcile_unknown` [Finding-1 correction — the ancestry direction]:** under a fresh committed read transaction, validate the authoritative chain (founding → head, every record and every referenced object hash-verified — the medium's rules). **`Installed { id }` iff HEAD equals the candidate OR the candidate appears in HEAD's validated ancestor chain** — i.e., the candidate is a member of the fully validated authoritative chain ending at HEAD (HEAD is the candidate or one of its descendants). **`NotInstalled { head }` iff the validated chain does not contain the candidate.** **`Unverifiable { reason }` iff the chain cannot be validated** (corruption, unreadable state) — the genuinely-unverifiable class is preserved exactly; uncertainty is never converted into a guess. (Revision 1 of this document stated the direction backwards — "head is the candidate or an ancestor" — which would classify a never-installed candidate whose descendant never existed as installed only by luck of phrasing; the corrected contract is head-or-descendant membership in the validated chain.)

**The transaction-outcome classification table [Finding-1]:**

| Failure point | Classification | Rationale |
|---|---|---|
| Any error before the first write operation (the head read, the parent compare) | Typed retryable error | Nothing written; SQLite's isolation guarantees no visibility |
| BUSY at `BEGIN IMMEDIATE`, within the timeout | Retried internally | Contention, not an outcome |
| BUSY timeout expiry (the write lock unavailable) | Typed contention error | Nothing began — never `Unknown`; never stale (no verified parent change) |
| Parent mismatch under the committed read | `RejectedStaleParent { observed }` | A genuinely changed authoritative parent, verified |
| An existing object row whose stored bytes fail the hash | `HashMismatch` (typed, fail-closed) | The referenced-corruption case; the transaction rolls back cleanly |
| The record insert violating `records_idem_unique` | `Chain { duplicate-idempotency-key }` (typed) | The chain rule; nothing installed; retry only with corrected input — never `Unknown` |
| A write failure mid-transaction (`SQLITE_IOERR`/`SQLITE_FULL` on an insert) | `ROLLBACK` succeeds → typed error; **the `ROLLBACK` itself fails → `Unknown`** | A failed rollback leaves the transaction's disposition in doubt — reconcile |
| `COMMIT` returns an error (`SQLITE_IOERR`/`SQLITE_FULL`/BUSY-on-commit) | **`Unknown` → `reconcile_unknown`** | The commit may or may not have installed; never guessed |
| `COMMIT` returns success | `Accepted { id, TransactionalWalFull }` | The linearization boundary |

**Every object required for an acknowledged canonical revision is inside the one transactional boundary** — the v1.8's requirement (3), satisfying the GO's explicit warning: no separately stored external blobs exist.

### 3.3 The durability tier and the platform boundary

WAL + `synchronous=FULL` + the documented commit semantics → `SyncTier` gains one additive variant (e.g., `TransactionalWalFull`): acknowledged-revision persistence across process crash, OS crash, and power loss, on all three platforms, per the documented SQLite contract (not a test claim — the testing-honesty rule applies identically: process-kill fault injection verifies the process-crash tier; the broader tier rests on documented semantics, now documented by a database engine whose core business is exactly this guarantee). `durability_tier()` returns it; `Accepted` carries it. The existing variants remain (the file medium's tiers unchanged). **The v1.8 §5.3.1 tier table gains a row, never a silent upgrade of the old ones.**

### 3.4 Validation, the trusted cursor, and readers

`validate()` walks the chain via the records table (head → parent links → the founding record; every record's `bytes` hash-verified; every `content_refs` object hash-verified; the chain rules enforced — epoch progression, parent coherence, founding presence, campaign-id coherence; the `records_idem_unique` constraint double-checked by the walk for the migrated-parity case). The §5.3.2 trusted-cursor model carries over unchanged in semantics: session-scoped in-memory derived state; O(1) per append (the new record's parent must equal the cursor's verified head); suffix-walk on divergence; sound invalidation forces the full walk; no persistent cache. **The audit mode improves materially:** a read-only connection takes a WAL snapshot — the full walk never blocks the writer (with the file medium, the audit walk holds the lock for its duration). Tooling and verification gain a non-interactive read path.

### 3.5 The WAL lifecycle and checkpoint policy

The `-wal`/`-shm` sidecars live beside `store.db`. In operation: SQLite's auto-checkpoint (the default passive 1000-page cadence). At the graceful session close and before any file-level copy, export, or backup that is not `VACUUM INTO`: a `TRUNCATE` checkpoint. **A live WAL-mode database is never file-copied without a checkpoint under quiescence** — the documented backup rule (§6.2).

### 3.6 Failure model and corruption

A corrupt page/structurally unreadable DB surfaces as typed Io/`CorruptHead`-class errors — fail closed, never silently repaired; the chain validation remains the semantic validator on top (a record/object hash mismatch is the same referenced-corruption fail-closed case as the file medium; evidence is preserved — with SQLite the "evidence" is the DB file itself, never modified in place by the engine outside transactions). The `sqlite3` CLI `.recover` tool is documented as an **owner-operated escape hatch, out of engine scope** — the engine never attempts automated repair. Quarantine as a storage-layer protocol disappears (there are no orphan files — an uncommitted transaction leaves nothing); the v1.8 §5.3.3 orphan semantics apply to the file medium, which remains the reference.

### 3.7 The T1 journal stays a file [PROPOSED — D-PP-2]

The journal is already power-loss-honest on both platforms [RATIFIED, the B3 implementation]: single-file append-only, the write handle opened with WRITE access so `sync_all` works on Windows (`FlushFileBuffers` — the B2 lesson), one fsync per completed transaction, hash-chained frames with the torn-tail/committed-corruption rules. 3. **The active state** — full fidelity (the queues, blocked, held, the world, the director, the materialization evidence).
4. **The unconfirmed/pending T1 intents, their deactivation plans, and the cancellation records** — until confirmed-or-canceled (the B3 supersession contract; §4.4's survival rules).
5. **The current anchor plus the retention window of prior anchors** (the P0-4 rule: the new anchor verified before the older become eligible).

**Summarized or reclaimed [PROPOSED — the protocol]:**

1. **The execution-history records below the compaction cut** — replaced by the prefix summary (§4.1) inside the compacted anchors.
2. **The pre-checkpoint snapshot objects** (the old full-fidelity session images) — superseded by verified later anchors per P0-4.
3. **The non-confirming publication revision records below the checkpoint** — the save-point-cadence revisions whose content objects are the reclaimed snapshots. (The *confirming* revisions are class 1 above and are never part of this term.)
4. **The retired T1 journal frames** — per §4.4's survival rules, after the checkpoint anchor that subsumes them is verified.

**Revision 1's contradiction, resolved [Finding-2]:** Revision 1 allowed "the prefix copies of confirming revisions" to be reclaimed below checkpoints (its eligibility rules 2–3) while simultaneously claiming the confirmed lane is "deliberately linear-KB retained" — an inconsistency with the ratified "retained in full" rule it cited. **The corrected default: confirming revisions and their consequence-batch objects are never reclaimed** (the linear-KB class of §4.3's arithmetic). **The alternative — reclaiming fully-materialized-and-confirmed evidence below checkpoints by promoting the checkpoint anchor's materialized coverage to the durable suppression authority for those identities — is a change to a RATIFIED retention rule and is presented as D-PP-4a [PROPOSED, explicitly NOT ratified], requiring an explicit owner decision.** What D-PP-4a would demand if ever approved: the anchor carrying a per-key digest of the confirmed set it subsumes; the B3 reconcile's Contract A consulting the anchor's coverage (tier-3 suppression) instead of the chain's per-key records (tier-1) for the reclaimed identities; the acceptance that the audit surface for those identities shrinks to the digest. The default recommendation is **not** to approve it.

**The digest distinction [Finding-2]:** while the source records below a checkpoint are retained, the compacted walk **recomputes** the prefix digest against them and compares — a verification. After reclamation, the retained digest is a **previously verified commitment**: a witness that the records were walked and hashed at a moment when they existed, chained from the founding record — **never an independent validation of unavailable history**. No claim in this design says a hash alone validates what it cannot read.

**How the B4 recovery and the B3 reconcile operate on compacted snapshots [Finding-2]:**
- The **B4 ledger-origin `RecoveryAnchor`** is constructed from the compacted anchor's per-identity lane aggregates and coverage boundaries — writer-computed carried values, authenticated by the anchor's content hash and proven conserving by the extended load gates. The recovery does not read per-execution records at all (it never did — the B4 anchor construction reads the ledger's per-identity *lanes*, which the aggregates carry); nothing is fabricated because nothing is inferred — the aggregates are the retained representation of exactly those lanes.
- The **B3 reconcile (Contract A)** applies still-missing occurrences against the working coverage via `missing_against` — the anchor's materialized coverage (tier 3) exactly as today. **Confirmed-but-unmaterialized or partially-represented effects are detected by the retained evidence alone:** the confirmed set (class 1, retained in full) minus the anchor's coverage boundary — both inputs retained, the computation unchanged.
- **A retired identity cannot reappear, collide, or require unavailable history [Finding-2]:** identities allocate under the monotonic ConsequenceId/episode frontier (class 2, never reclaimed) — a retired identity's range lies strictly below the frontier and new identities allocate strictly above, so no reuse or collision is representable; and the eligibility rule for summarizing an identity **required** that no outstanding obligation, pending intent, or unmaterialized confirmation reference it — so no recovery path can encounter work that needs its per-record history. The frontier monotonicity through save/restart/transitions is a proven B4 regression invariant [RATIFIED].

**The checkpoint revisions, the skip table, the compact reclaimed-record index, and the post-reclamation validator [PROPOSED — the re-review's findings, refined]:** a compaction publishes through the normal append (the v1.8: "a compaction IS a new snapshot revision on the chain") — a regular revision whose content object is the compacted session anchor (§4.1's form + the director state + the materialization evidence, the existing `session-snapshot/1` composition with the compacted spine section) **plus the skip table, the compact reclaimed-record index, and the chain-prefix digest (the bounded representation below)**.

**The skip table and the compact reclaimed-record index — the structural fix for the parent-link problem, bounded where the ratified contracts allow [the re-review's Finding-2 corrective]:** the accepted `RevisionRecord` stores a parent hash and the medium's walk requires a complete verifiable parent chain, so reclaiming a non-confirming publication revision that remains the parent of a retained confirming revision would break that chain. Revision 3 answered with a full per-record skeleton — which preserves ancestry structurally but **retains O(number of reclaimed revisions) metadata and makes the post-reclamation walk traverse every historical skeleton entry: lifetime-growing, exactly the growth the re-review identified; that representation is replaced here**. The corrected design partitions what the validator actually needs:

- **The skip table [bounded by the retained set]:** for every RETAINED record whose parent is reclaimed, the checkpoint carries a precomputed skip — (the record's identity → its NEAREST RETAINED ancestor's identity) — computed at reclamation time, when the full span was walked and digest-attested. The walk never traverses intermediate reclaimed entries: it jumps from a retained record directly to its nearest retained ancestor. The table's size is O(retained records with reclaimed parents) — the confirming-revision class (the §4.3 confirmed lane, deliberately retained in full), **NOT O(reclaimed publications)**.
- **The compact reclaimed-record index [two DISTINCT identity classes, per the Rev-4 re-review's Finding-2 — linear-lifetime at ~80 B per reclaimed record, quantified below]:** the reclaimed records carry two unrelated identity classes the validator needs: (a) the **idempotency keys** (`RevisionRecord.idempotency_key` — logical operation deduplication: a new record reusing a reclaimed key would violate the chain-wide uniqueness the B3 pipeline's dedup depends on — a RATIFIED guarantee not silently relaxed); and (b) the **revision identities with their epochs** (the record's content hash + its chain position — what surviving `depends_on` references name: the B2 chain rule requires a dependency to name a strictly earlier revision of the authoritative chain, and **an idempotency-key set proves nothing about a revision hash's existence or order**). Each checkpoint's index carries, **for its own reclaimed range only**, the sorted {idempotency key (where present), revision hash, epoch} entries. **The index is lifetime-growing and deliberately so**; the alternatives — window-scoped key uniqueness (**D-PP-4b**, a change to a ratified guarantee, recommended NOT to approve) and declaring `depends_on`-referenced revisions ineligible for reclamation (the conservative fallback: a revision named by any surviving `depends_on` is retained — viable, but retained confirmations' dependencies would pin their referenced publications indefinitely, defeating the reclamation for those records) — are both presented for the owner; **the recommended default is the index**.
- **The digest chain [O(checkpoints)]:** the SHA-256 chain over each reclaimed range's record bytes (the previously-verified commitment — attesting what was skipped, never revalidating it; the recomputed-against-retained vs previously-verified-commitment distinction of the digest paragraph above applies unchanged).

**No existing `revision-record/1` byte or content hash is ever rewritten** — the retained records stand verbatim; the skip table and the compact reclaimed-record index are new, checkpoint-carried, and cover only the reclaimed.

**The post-reclamation validator (the compacted walk — the cold-open claim corrected [Finding-2]):** from HEAD, walk parent links through retained records verbatim (hash-verified, the existing rules — epoch progression, parent coherence, founding presence, campaign-id coherence). When a retained record's parent is reclaimed, consult the covering checkpoint's skip table: **jump directly to the nearest retained ancestor** (the skip is the checkpoint's writer-computed attestation — the same trust class as the compacted anchor's carried values, digest-backed for the skipped span). Continue until the founding record (**never reclaimed — the authority root**). **The coherent membership semantics [the review's requirement]:** the effective membership universe is ONE definition shared by append, cold-open validation, and Unknown-outcome reconciliation — a revision identity exists iff it is a retained record OR an index entry (hash + epoch); an idempotency key is spent iff it is a retained record's key OR an index key; a `depends_on` reference resolves iff its target exists in that universe AND its epoch is strictly earlier than the referencing record's (the retained records' own epochs + the index's epochs). The append's duplicate-key check, the cold-open walk's dependency checks, and `reconcile_unknown`'s chain validation all consult this same universe — no operation sees a different membership. **What the skip table can and cannot independently establish [the review's requirement]:** the skip is the checkpoint's writer-computed attestation (content-hashed, chain-published, digest-backed for the skipped span — the same trust class as the compacted anchor's carried values). It CAN establish: the retained record's ancestry passes through the named retained ancestor, as computed and attested at reclamation time when the full span was walked and verified. It CANNOT independently establish: the skipped records' bytes, their semantic validity, or any property beyond the digest's previously-verified commitment — after the original record bytes are reclaimed, the ancestry is as attested, never independently re-derived. **The corrected cost model: the post-reclamation cold open is O(retained records + the skip tables + the compact reclaimed-record indexes) — linear in the retained confirming count and the lifetime reclaimed-record count, NOT bounded by the checkpoint interval** (Revision 3's checkpoint-bounded claim was wrong and is withdrawn). It remains a strict improvement over the pre-compaction walk (linear in ALL revisions — the reclaimed publications' bytes and content objects are no longer read at all), and its growth classes are exactly the two §4.3 scopes honestly: the confirmed lane (deliberate) and the reclaimed-record index (deliberate, quantified). The §7.3 cold-open targets are revised accordingly. **The `CanonicalMedium`/`ChainSummary` reconciliation [PROPOSED, explicitly labeled — as in Revision 3]:** `validate()` gains the compacted walk mode; `ChainSummary` gains additive checkpoint-attestation fields (the reclaimed counts, the checkpoint identities, the digest chain); the pre-reclamation behavior is byte-identical to today's. **What the digest attests / what remains independently verifiable / what is deliberately no longer verifiable:** the digest attests that the reclaimed records' bytes were walked and hashed at reclamation time; independently verifiable post-reclamation: the retained records, the skip tables, the compact reclaimed-record indexes, the checkpoint itself, and the founding root; deliberately no longer verifiable: the reclaimed records' bytes, their content objects, and any per-record semantic check over them.

**The worked examples (single- and multi-checkpoint, one valid chronological parent chain throughout — the Rev-4 example's chain error corrected):** *Single checkpoint:* the chain `F ← S1 ← C1 ← S2 ← S2′ ← C2 ← K1` (K1.parent = C2). K1 reclaims {S1, S2, S2′}, retaining {F, C1, C2}. K1's skip table: {C1 → F} and {C2 → C1}; K1's index: the keys {k1, k2, k2′} + the identities {hash(S1)/epoch 1, hash(S2)/epoch 3, hash(S2′)/epoch 4}. The walk: K1 → C2 → skip → C1 → skip → F. *Multi-checkpoint:* the campaign continues **on top of K1** — the chain extends `F ← … ← C2 ← K1 ← S3 ← C3 ← S4 ← C4 ← K2` (K2.parent = C4; K2's range is the records between K1 and K2). K2 reclaims {S3, S4}, retaining {C3, C4}. K2's skip table: {C4 → C3} (S4's nearest retained ancestor is C3) and {C3 → K1} (**S3.parent = K1, retained** — the corrected link); K2's index: the keys {k3, k4} + the S3/S4 identities. **The walk from HEAD: K2 → C4 → skip → C3 → skip → K1 → C2 → skip (K1's table) → C1 → skip (K1's table) → F** — K1 and K2 in ONE chronological parent chain, every skip resolving to the correct nearest retained ancestor. *A `depends_on` reference across ranges:* if C3 carries `depends_on [hash(S2′)]` (a reclaimed revision of K1's range), the resolution: hash(S2′) exists in K1's index with epoch 4 < C3's epoch — existence + strictly-earlier order verified against the index, exactly the distinction the review requires (the idempotency-key set alone could not prove it).

**The growth quantification [EXTRAPOLATED from MEASURED rates — the arithmetic corrected per the review]:** the skip table grows with the retained confirming revisions (~200 B per skip — the confirmed-lane class); the reclaimed-record index grows at ~80 B per reclaimed publication record (the key + the hash + the epoch) — at the fixture's one-publication-per-minute policy (60/h) ≈ 4.8 KB/h ≈ **~48 KB per 10-hour session** (Revision 4's "~240 KB" multiplied the hourly rate by ten — the keys alone are ~24 KB at 60 × 40 B × 10 h; the index's identity entries add the rest; corrected); vs the reclaimed content's ~15–25 MB/h — a ~300–500× reduction, but **NOT bounded**; the per-checkpoint serialization is O(its own range) — ~32 index entries + a few skips + the compacted anchor (~250–400 KB, the dominant term), with no cumulative re-serialization across checkpoints.

**The crash/reclamation matrix:** (a) crash before the checkpoint commits — nothing reclaimed, the normal walk; (b) crash after the checkpoint commits, before the deletes — the records still present; the skip table is redundant; the validator prefers the records (the deletes are the switch — the records-or-skip rule); (c) crash mid-delete — idempotent by content addressing (a re-run deletes only what remains); (d) after the deletes — the compacted walk as spec'd. **No reachable state breaks the retained confirmations' chain-reachability.** Cold-open cost post-reclamation: O(retained records + the skip tables + the compact reclaimed-record indexes) — **linear in the retained confirming count and the lifetime reclaimed-record count (the corrected model above), never presented as checkpoint-bounded**.

**The reclamation procedure (two-phase, interruption-safe):** (1) the eligibility mark — a reclamation-ledger revision (a normal chain revision recording what becomes eligible: the digests, the class, the cut) — itself verified before anything is touched; (2) the reclaim — the DB deletes (the prefix snapshot objects and non-confirming records), the retired journal files, the superseded snapshot objects — idempotent by content addressing (a re-run deletes nothing already gone). Interruption anywhere: the anchor/HEAD state is unchanged by reclamation; the reclaim is restartable. **A reclamation is never automatic at first implementation** — PP-B3 delivers it behind an explicit, logged operation (the owner-invoked or policy-invoked with the reclamation ledger as the audit trail).

**What remains reconstructible vs deliberately unavailable after reclamation (the truth table):** *Reconstructible:* the active state in full; the frontiers; the per-identity aggregates and coverage boundaries; the retained window's per-record history; the retained confirmed-lane evidence in full (class 1); the authenticated digests of the reclaimed prefixes — verifiable claims about *what* was discarded, never its content. *Deliberately unavailable:* the per-execution records below the cut (which NPC, when, which schedule-kind); the historical `engine_fingerprint`/`lane_fingerprint` of pre-cut states; the full `ledger()` below the cut; the pre-checkpoint snapshot objects and non-confirming revision bytes (post-reclamation — the digest stands in); any audit requiring those original bytes. The design never silently returns partial history as complete [RATIFIED, §5.6.2's retention-truth rule].

## 5. Gameplay-safe persistence orchestration (objective 3) [PROPOSED — D-PP-5]

### 5.1 The measured cost structure and the frame budgets

At the rig's dev-profile numbers: the journal transaction (4.337 ms) and the confirmation (7.526 ms) each fit a 60 FPS frame budget (16.667 ms) but exceed 144/240; the publication (57.750 ms) fits none; the serialization (~12.076 ms at 4,800 ticks) fits 60 only at short durations and grows linearly. **With §4's compaction the serialization is bounded** (O(active + window) — the steady-state scale); **with the background publication (below) the fsync sequence leaves the calling thread**; the journal transaction and the confirmation remain synchronous boundary costs by design (the T1-before-T3 sequencing; the pipeline's verified read-back). The 144/240 FPS targets then hinge on: the release-mode re-measurement (§7.2) and the boundary-operation cadence policy (the confirmation occurs per deactivation boundary, not per frame — its amortized per-frame cost is the deactivation rate × 7.5 ms; at the fixture's ~one per 55 ticks ≈ 0.14 ms/tick amortized). **No frame-responsiveness claim is made beyond the measured numbers; §7.2's release-mode run is the gate for any stronger statement.**

### 5.2 The single-authority ordering protocol (the P0-6 "I/O-worker ownership boundaries designed," made concrete; Finding-4 corrective)

**The one serialization point [Finding-4]: ALL canonical-medium writes route through the single I/O worker** — the snapshot publications (asynchronous) **and** the canonical confirmations (synchronous enqueue-and-wait: the authority thread enqueues the confirmation job and blocks on its result). The authority thread performs: the T1 journal transactions (the separate file medium — no chain interaction, and the journal receipt strictly precedes the confirmation's enqueue, preserving the T1-before-T3 contract), the capture (the bounded post-compaction serialization; the clone-handoff alternative is **DEFERRED** pending the release-mode capture measurements), and the enqueue/report plumbing. **The worker owns the campaign's one medium connection; the recovery path opens its own at session start (single-threaded, before the worker exists).** FIFO across the single queue now covers every canonical write — there is no canonical write outside it.

**The stale-snapshot scenario and its resolution [the re-review's Finding-4 corrective — reject-and-regenerate; a state image is never rebased]:** every capture records its **causal frontier** — F_c = (the canonical head H_c observed at capture time, the journal's last committed transaction J_c, the session's consequential-state coverage the captured bytes represent). A queued snapshot is captured at H_c; a confirmation ahead of it in the queue commits and advances HEAD. When the worker executes the snapshot's append, the committed read observes head ≠ H_c → `RejectedStaleParent`. **The admissibility rule: the publication is admissible iff the current head is still exactly H_c** — otherwise the queued snapshot is **REJECTED (dropped) and reported stale; the authority thread re-captures fresh bytes at the next boundary** (the new capture's frontier includes the current head and everything it represents). **Why no rebase for state images [the review's point]:** a newer parent and revision epoch prove ordering, not that the snapshot's bytes contain or can reconstruct all earlier confirmed effects — a rebased stale image would become the chain's LATEST snapshot with a frontier predating confirmations whose journal evidence may since have been rotated or reclaimed, exactly the situation the accepted regression `recovery_fails_closed_on_confirmed_unmaterialized_without_evidence` proves unrecoverable. **The two rebase classes are distinct:** the B3 pipeline's stale-parent rebase remains for **confirmation batches** (per-key consequence evidence, identity-addressed, evidence-backed — a ratified mechanism); **snapshot publications (state images) reject-and-regenerate, always.** **The newest-snapshot frontier never regresses** — a published snapshot's frontier includes everything the then-current head includes; the discovery's latest-snapshot rule and the retention/rotation rules (which retire journal evidence only after a verified anchor — at-or-above every later-published snapshot's frontier — materializes it) hold invariantly. The rotation interaction: a capture whose frontier predates a rotation is rejected by the same rule (the head advanced through the checkpoint) and regenerated post-rotation. **The required regression [the review's]:** snapshot-captured-before-confirmation / worker-executes-after → rejected + regenerated, asserted by test; crash recovery (an in-flight publication at crash = the committed-or-not state + the §3.2 reconcile; a rejected one leaves no chain state); the retention interaction (the anchor-window invariants above). **UI honesty:** a rejected publication reports the typed stale result — never "saved"; no false saved/confirmed claims. The re-capture cost is tolerated by the publication-cadence policy (the save point is periodic; the rejection frequency is bounded by the confirmations that land ahead of a queued capture).

**Ordering of the operations (the complete list) [Finding-4]:** the journal transaction (authority thread, synchronous, receipt before anything canonical) → the confirmation (enqueue-and-wait; the pipeline's `commit_canonical` returns only after the worker's committed transaction AND the verified read-back — the no-false-confirmation contract preserved; the wait is bounded by the queue depth ahead of it plus one transaction) → the snapshot publications (asynchronous; completions reported with the outcome + tier; the crossing's caller receives typed busy/stale/accepted results) → the recovery (session start, single-threaded, before the worker exists) → the graceful close (drain the queue, the TRUNCATE checkpoint, exit).

**Backpressure, split by dependency [Finding-4]:** the **optional** publication (the periodic save point) — a full queue returns the typed busy result; the campaign continues; the publication drops or defers (the content-hash idempotency absorbs retries). The **required-durability** operations (every confirmation; the graceful close's final publication) — the caller **waits** (enqueue-and-wait; FIFO service bounds the wait by the drain; a worker that cannot serve fails closed rather than silently skipping). **The governing gameplay rule, retained verbatim from the accepted design: simulation may continue during pending saves only while verified exclusive authority remains intact, and irreversible actions dependent on unconfirmed progress remain gated.**

**Cancellation, shutdown, and failure [Finding-4]:** cancellation drops queued-but-unstarted publication jobs only (a started transaction runs to completion — atomicity); the shutdown drains + checkpoints; **worker failure** (the thread dies / the connection breaks) = the medium unavailable → the crossing fails closed (HALT authoritative progression); the started jobs' dispositions become `Unknown`-class and are reconciled at the next session's recovery via the §3.2 `reconcile_unknown` path; unstarted jobs are simply gone (their operations were never reported complete). **Unverifiable exclusive authority** (a persistent foreign writer, a corrupt DB) fails closed — the existing ratified contract.

**Scope discipline:** this section is design-only. **No threading is introduced in production code by this phase** (the GO's rule); the worker is PP-B4's deliverable behind its own GO.

## 6. Migration, backup, and compatibility (objective 4) [PROPOSED — D-PP-6]

### 6.1 The staged migration with the seal-first authority transfer and the offline-conversion procedure (the Rev-4 re-review's Finding-1 corrective)

**The staged, idempotent copy:** (1) **read** the existing store via the `LocalFileMedium`'s own verified walk (`validate()` — founding→HEAD, every record and object hash-verified; the old store is never modified); (2) **write** into the target DB — the objects and records as content-addressed idempotent inserts (restartable; a re-run inserts nothing new), the chain rules verified as each record lands; (3) **verify** — the DB's `validate()` must produce the **identical `ChainSummary`**.

**The seal-first authority transfer [the re-review's Finding-1 corrective — the target cannot activate before the source is durably sealed]:** (4) **acquire the source store's `HEAD.lock`** — the OS-managed exclusive lock, **held across the entire transfer** (the file medium's per-operation locking means every other process's medium operation on the source blocks for the duration; a handle opened before the transfer began must acquire the lock for its next operation — it blocks, then hits the admission check below); (5) **re-verify the source head** under the held lock (it must still be the migrated head H — an intervening foreign write is the divergence case: fail closed, never merge); (6) **seal the source durably — BEFORE anything activates the target**: write the `MIGRATED` tombstone (tmp + fsync + rename + the directory fsync where the platform exposes it — the same discipline as the medium's own HEAD publication) recording the target's identity. **From this instant every future source operation refuses — the source-side admission check lives in the `LocalFileMedium` open/append path itself** (acquire the lock → check the tombstone → refuse fail-closed), so **previously opened handles are admitted through the same check at their next operation**; (7) **the fail-closed intermediate**: between the durable seal and the target's activation, **neither store accepts authoritative progression** — the source is sealed (every admission path refuses), the target is not yet authoritative (its `meta.provenance` marker absent or in a `PENDING` state that the open path refuses); (8) **activate the target**: commit the DB authority marker (`meta.provenance`: the source identity, the path, the migrated head H, the seal's attestation, the timestamp) in one transaction — the only step that makes the target authoritative, and it is **strictly after the durable seal**; (9) release the lock. **The ordering invariant: the target cannot accept progression before the source is durably sealed.**

**The crash-window table — no reachable state admits two authoritative writers:**

| Crash point | Source | Target | Dual authority? |
|---|---|---|---|
| Before the lock / during the copy (1)–(3) | Authoritative (unsealed) | Not authoritative (no marker) | **No** — only the source |
| During the seal (6): the tombstone's tmp+rename in flight | Either unsealed (the tmp discarded → the pre-migration state) or sealed | Not authoritative | **No** — at most the source |
| After the seal, before the activation (7) | **Sealed — refuses** | **Not authoritative — refuses** (the fail-closed intermediate) | **No — neither store** |
| During the activation (8): the marker transaction | Sealed | SQLite-atomic: unmarked (the intermediate persists) or marked | **No** |
| After the activation | Sealed forever | Authoritative | **No** — only the target |
| **Power loss after the activation, the seal's directory metadata lost (Windows — the cross-medium asymmetry)** | Apparently unsealed (an older client could open it) | Activated (WAL/FULL survives) | **Possible — prevented only by the offline procedure's archival** (§ below) |

**The recovery from the intermediate:** the migration tool re-runs — the sealed source + the unmarked target is a resumable state (the copy is idempotent; the seal's presence is verified; the activation completes).

**The initial feature is the offline conversion — the operator-controlled procedure, with the mechanically enforced claims scoped honestly [the Rev-4 re-review's Finding-1 corrective]:** an **automated, mechanically power-loss-safe authority transfer cannot be established under the current primitives** — the source's de-authorization lives in the file medium (whose acknowledged Windows power-loss tier is unclaimed from std), **and the archive rename itself shares that tier** (Windows std does not guarantee the rename survives power loss), so the window between the SQLite activation and the archival is real and cannot be closed by any file-medium operation. The design does not claim it. **What is claimed, exactly:**
- **Process-crash safety, mechanically enforced, on every platform** — the seal-first transfer with the fail-closed intermediate (unchanged; the crash-window table's process-crash rows stand).
- **Power-loss safety only through the operator-controlled offline procedure** — documented operator responsibility, never a mechanism claim.

**The procedure's state machine — when the source becomes inaccessible to old binaries, and when the target becomes eligible for gameplay:**
1. **Copy + verify** (the staged idempotent copy; the `ChainSummary` parity): the source authoritative, the target inert.
2. **Seal** (the tombstone under the held lock): the source refuses for tombstone-aware clients; the target still inert.
3. **Activate** (the DB marker transaction): **the target becomes the only store NEW binaries treat as authoritative — but the source is NOT yet inaccessible to old binaries** (an old binary at the original path can still open it; this window is the operator's to close, and a power loss here is addressed by the recovery below).
4. **Archive** (the source directory renamed out of the standard campaign path): **from this step the source is inaccessible to old binaries at the original path** (a directory rename is atomic to observers; its power-loss durability carries the file medium's documented tier).
5. **Verify — the operator's checklist, the gameplay-eligibility gate:** the operator confirms the source is NOT at the original path and the target opens and validates. **The target is eligible for gameplay only after this verification** — the gate is the completed checklist, not an automatic state.

**The power-loss windows and the supported recovery:** power loss after the activation but before or during the archival leaves the DB authoritative and the source at its original path (sealed for supported clients if the seal survived; unsealed if not) — **the supported recovery procedure: re-run the migration tool** (it detects the activated target + the source at the original path → completes the archival; if the source's head changed in the window — an old binary wrote to it — the tool detects the divergence and **fails closed**: the divergent writes are confined to the legacy store, never merged; the operator resolves explicitly (forfeit or manually reconcile), documented). **If the source reappears at its original path later** (an operator restore, an undo): the same re-run recovery applies; a supported client pointed at it by mistake is caught by the tombstone if the seal survived, or by the operator's verification discipline otherwise. **The design does not claim universal dual-authority prevention where an older executable can still open the legacy store** — that prevention is the operator's archival + verification, stated as responsibility.

**The acceptance tests [PP-B1]:** the process-kill matrix (the process-crash tier — every crash-window row asserted); **the offline-conversion checklist test** (the tool completes the archival; the gameplay-eligibility gate requires the verified checklist); **the source-reappears recovery test** (the re-run completes the archival or fails closed on divergence — never merges); the tombstone-aware refusal on the sealed source; the older-binary divergence documented as archive-confined; **no test claims power-loss durability — process-kill tests establish the process-crash tier only** (the testing-honesty rule; the power-loss rows rest on documented semantics + the operator procedure, never on tests).

**Rollback and downgrade:** pre-cutover — trivial (the old store is intact and authoritative); post-cutover — the export path (§6.3) rebuilds a file store from the DB, or the retained old store serves until the DB advances beyond it. Downgrade after advancement: **refused, with the export path documented** (the explicit, non-silent rule). The cutover itself is the caller's store-path change (the crossing opens the DB; the marker verified at open).

### 6.2 The quiescent-boundary campaign backup (the re-review's Finding-2 corrective)

**A consistent campaign-wide recovery point spans TWO artifacts — the SQLite database and the separate T1 journal — and `VACUUM INTO` alone atomically snapshots only the first [the re-review's Finding-2 corrective].** Revision 2's online journal-first/DB-second ordering claimed both pair-orderings recoverable; that claim is **falsified by the accepted Stage 5 regression `recovery_fails_closed_on_confirmed_unmaterialized_without_evidence`**: a consequence confirmed BETWEEN the two captures appears in the DB image with its T1 transaction absent from the journal copy, and an anchor predating the confirmation leaves the effect confirmed-but-unmaterialized without journal evidence — unrecoverable, fail-closed. **The corrected protocol is the quiescent boundary (the review's sanctioned safe initial protocol):** (1) **quiesce** — the authority thread reaches a boundary with **no boundary operation in flight** (the §5.2 queue drained or paused; pre-orchestration, the synchronous design's natural between-operations boundary): no journal append, no canonical write, no rotation can interleave; (2) **capture the pair under quiescence**: the T1 journal copy (append-only with no writer — an exact copy; a torn tail is tolerated by the scan's inert-tail rules regardless) and the DB via `VACUUM INTO` (a transactionally consistent image at its head H); **the pair is coherent by construction** — every committed T1 transaction's effect is either materialized in the DB's chain state at H or pending in the journal copy, and **no confirmation can occur between the captures** (quiesced); (3) **write the manifest LAST, atomically** (tmp + rename) binding: the DB image's head H, the journal copy's SHA-256 and its last committed transaction J, the active journal path (the post-rotation identity), the checkpoint state, the quiescence marker, the timestamps.

**The usability verification [the review's requirement]:** a backup is labeled **usable** only after the **restored-session recovery verification** — the tooling restores the pair into a scratch location, runs the existing B4 recovery, and asserts a coherent session (the recovery's own gates) plus the `ChainSummary` parity at H; until that verification passes, the backup is marked unverified and never presented as a recovery point. **Interrupted-backup and manifest publication semantics:** no manifest = **not a valid backup set — refused**; a partial or hash-mismatched set is detected at restore and discarded; the manifest is the commit point (everything before it is scratch). **The boundary classes covered [the review's list]:** deactivation plans and cancellations live in the journal (copied complete under quiescence); Unknown outcomes — the journal's unresolved tail is copied verbatim and reconciled at restore (the §3.2 reconcile); simultaneous rotation — impossible under quiescence (the rotation is itself a boundary operation; the manifest records the active journal path); confirmation-between-captures — impossible under quiescence. **No-false-confirmation and exact-once are preserved**: the restore runs the same B4 recovery with the same contracts — the confirmed evidence is in the DB image, the pending intents re-drive exactly once, the four-state honesty holds. **The online (non-quiescent) capture is explicitly DEFERRED** — a genuinely online coherent boundary (e.g., a coordinated SQLite-snapshot + journal-boundary capture) is not proven here and is not claimed; the quiescent capture is the initial protocol, with the online path a future separately-proven extension behind its own evidence.

### 6.3 The original formats as independently verifiable references

The `LocalFileMedium` (reader and writer) is **retained permanently** — the reference implementation, the test oracle (the PP-batch equivalence suites run the same logical campaign through both mediums and compare `ChainSummary`s and recovered states), and the export/downgrade path. The B1 wire format, `revision-record/1`, and every versioned domain are unchanged by the provider swap; every frozen fingerprint is beneath the seam and mechanically preserved.
