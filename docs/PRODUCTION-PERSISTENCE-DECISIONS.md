## D-PP-1 — The canonical-medium storage provider (production)

- **The decision:** what backs the `CanonicalMedium` trait for production standalone campaigns.
- **Recommended default:** the **unified cross-platform SQLite-backed canonical medium** — one database per campaign (`objects`/`records`/`meta` tables; the canonical bytes verbatim as BLOBs, content-addressed by the same SHA-256), WAL + `synchronous=FULL`, every object required for an acknowledged revision committed in **one transaction** (objects + record + HEAD together; no external blobs), behind the **unchanged `CanonicalMedium` trait**. The `LocalFileMedium` retained permanently as the reference implementation, test oracle, and export path.
- **Basis:** the v1.8 §2.1/§5.3.3-E4 ratified SQLite as "the preferred production fallback" with exactly these requirements; the production gate it reserved has now fired — the Windows power-loss/OS-crash acknowledged-revision tier is not establishable from std (the N−1-valid/N-lost scenario), and the Stage 5 acceptance + the physical rig run are complete.
- **Alternatives considered:** (a) keep the custom medium everywhere — rejected for production (contradicts the v1.8's own acceptance rule for Windows standalone production); (b) the narrow Windows-specific module (`FILE_FLAG_BACKUP_SEMANTICS` directory flush / `MoveFileExW(MOVEFILE_WRITE_THROUGH)`) — **unproven** per the v1.8's evidence standard (documented handle acquisition ≠ documented flush durability; no authoritative documentation has surfaced), plus the engine's first platform-specific unsafe code and a two-medium durability story; documented as the fallback-of-the-fallback with that consequence stated.
- **Costs:** a new `engine-persist` dependency (`rusqlite` bundled — the C amalgamation via `cc`, statically linked); an additional native build path on CI/Windows/macOS (the SDL3/cmake lesson — audited as a PP-B1 gate); ~1–1.5 MB binary size; WAL/`-shm` sidecar files; a disciplined backup story (checkpoint before file copy; `VACUUM INTO` for online backup).
- **Risks:** the build-path maintenance on three platforms; dependency governance (a single well-known crate); SQLite's own semantics drift across versions (mitigated: pin the bundled amalgamation version; the engine's chain validation remains the semantic validator on top).
- **Evidence needed for approval:** the documented WAL/`synchronous=FULL` semantics (the abrupt-power-loss-safe setting; `NORMAL` does not meet the contract); the PP-B1 parity suite (the `ChainSummary`-identical reads of the same logical campaign through both mediums) **+ the DESIGN §3.2 transaction-outcome matrix exercised by fault injection** (the BUSY-timeout contention abort — never stale without a verified parent change; the successful-`COMMIT` linearization boundary; the `reconcile_unknown` direction — Installed iff the candidate is HEAD or in HEAD's validated ancestor chain; the preserved genuinely-unverifiable class; the failed-insert/constraint/rollback/commit-uncertainty classifications; the existing content-addressed rows) + the three-platform build audit + the migration interruption matrix. **Status: OPEN.**

## D-PP-2 — The T1 journal's placement

- **The decision:** whether the durable T1 journal moves into the same database.
- **Recommended default:** **keep the journal as its own file medium.** It is already power-loss-honest on both platforms (single-file append-only, the WRITE-access handle so `sync_all` works on Windows, one fsync per completed transaction, the hash-chained torn-tail rules) — the Windows gap does not exist for it; the T1-before-T3 two-domain sequencing is by ratified design; the fold-in buys no required atomicity.
- **Alternatives considered:** folding the journal into the DB (a journal table; one DB transaction per journal commit preserving the one-fsync contract) — **DEFERRED** with the trigger: a separately authorized consolidation batch, only after the medium swap is proven.
- **Costs of the default:** two storage artifacts to back up/migrate (the operational rule: a backup omitting the journal is not a campaign backup).
- **Risks:** minimal — zero contract drift; the B3/B4 recovery composes the two domains by design.
- **Evidence needed for approval:** none beyond D-PP-1 (this is a scoping default within it). **Status: OPEN (a sub-decision of D-PP-1).**

## D-PP-3 — The compacted session save, `spine-history/2`

- **The decision:** the versioned save form that bounds the spine's session-embedded execution history.
- **Recommended default:** the **ratified v1.8 §5.6/§5.6.1 architecture made concrete**: the cut, the authenticated prefix summary (the SHA-256 chain over the discarded records, seeded from the prior compaction), the unfinished-index derivation (`executed == [0, next_seq) \ unfinished`; `known == [0, next_seq)`), the writer-computed carried counters, the ratified load-gate list, the compacted domains (`engine-core/spine-compacted/1`, `engine-core/state-compacted/1`) — **plus the per-identity lane records** (the B4 extension the v1.8 predates; clarified per the re-review's Finding 3): an identity's lane state is retained **in full — the per-identity pending count, the applied count, AND the materialized-coverage boundary (the `(lo, hi]` ordinal range), exactly the `RecoveryAnchor`'s per-identity inputs — never aggregate totals alone** (the B3/B4 exact-identity reconciliation cannot infer individual materialization from totals) iff any outstanding obligation, pending T1 intent, or unmaterialized confirmed evidence references it; fully materialized-and-confirmed identities below the cut are summarized into the coverage boundary + the aggregate counters (retained as the conservation cross-checks), with the conservation gates extended to the lanes.
- **Basis:** [RATIFIED] the v1.8 Correction C architecture (complement-of-unfinished; the bitset alternative already rejected); [MEASURED] the ~31.0 B/execution linear growth the B5 sweep established.
- **Alternatives considered:** a stored executed bitset (rejected by the v1.8 erratum E3 — it grows one bit per ever-allocated id, unbounded); no compaction (rejected — the 10-hour extrapolation ~257 MB/snapshot with ~2 s serialization).
- **Costs:** a new versioned domain + the `HistoryKind` surface (the safe accessors `ledger_retained()`/`try_ledger_full()`/the `try_*` fingerprints — all specified by the ratified §5.6.1); the equivalence-test burden (the extended twin suite).
- **Risks:** the deliberate unavailability must stay honest (the historical fingerprints and per-record history below the cut are not reconstructible after reference reclamation — the truth table in DESIGN §4.2); the lane-aggregate extension is new design (not ratified) — it carries the PP-B2 equivalence burden specifically.
- **Evidence needed for approval:** the PP-B2 gates — every historical fingerprint byte-identical on `Full` instances; the twin-equivalence suite (the compacted image's continuation behavior identical to the uncompacted control, including the B4 recovery from a compacted anchor); the steady-state size/capture measurements confirming the projections. **Status: OPEN.**

## D-PP-4 — The retention/rotation protocol and its numerical defaults

- **The decision:** how the chain, journal, snapshots, and quarantine are bounded (the second lifetime-growth dimension).
- **Recommended default:** the **checkpoint/rotation/verify-before-reclaim protocol** (DESIGN §4.2/§4.4): the checkpoint revisions carrying the compacted anchor + the chain-prefix digest **+ the skip table and the compact reclaimed-record index** (DESIGN §4.2, the second re-review's Finding-2 corrective: Revision 3's full per-record skeleton was itself lifetime-growing — replaced by the bounded representation: **the skip table** (for every RETAINED record whose parent is reclaimed, the precomputed skip to its nearest retained ancestor — O(retained records), the confirming-revision class, NOT O(reclaimed publications); the walk never traverses intermediate reclaimed entries) + **the compact reclaimed-record index** (DESIGN §4.2, the Rev-4 re-review's Finding-2: the `idempotency_key` (logical dedup) and the revision hash + epoch (what surviving `depends_on` references name) are DISTINCT identity classes — an idempotency-key set proves nothing about a revision hash's existence or order; the index carries, per checkpoint, its own reclaimed range's sorted {key, hash, epoch} entries, ~80 B per record — linear-lifetime at **~48 KB per 10-hour fixture session** (the Rev-4 ~240 KB figure was a ten-fold arithmetic slip — the keys alone ~24 KB at 60/h × 40 B × 10 h), REQUIRED by the ratified chain-wide idempotency-key uniqueness AND the `depends_on` revision-identity resolvability (existence + strictly-earlier order), NOT silently relaxed; the conservative alternative — depends_on-referenced revisions ineligible for reclamation — presented with its consequence (retained confirmations' dependencies pinning their publications); the recommended default: the index) + the digest chain; **no existing revision-record/1 byte or content hash is ever rewritten**; the post-reclamation validator walks retained records verbatim and jumps via the skips — **the cold open is O(retained records + the skip tables + the compact reclaimed-record indexes), linear in the retained confirming and lifetime reclaimed-record counts, NOT checkpoint-bounded (the corrected claim); the coherent membership semantics — one universe shared by append, cold-open validation, and Unknown-outcome reconciliation (a revision identity exists iff retained or an index entry; a key is spent iff retained or indexed; a `depends_on` resolves iff the target exists in that universe with a strictly-earlier epoch); the skip-table authentication statement (what it can — the attested ancestry — and cannot — anything about the reclaimed bytes beyond the digest — independently establish); the multi-checkpoint example corrected to ONE valid chronological parent chain (S3.parent = K1 — the retained checkpoint in the chain), every skip resolving to the correct nearest retained ancestor;** the multi-checkpoint structure: successive checkpoints carry only their own range — no cumulative re-serialization; the founding record is never reclaimed); the T1 journal rotation at checkpoints under the **exact survival rules** (unconfirmed transactions, their deactivation plans, cancellations, confirmed-but-unmaterialized effects, and Unknown-outcome evidence always survive; only fully-materialized-and-confirmed effects retire after a verified anchor subsumes them) with the **recovery matrix** for crashes before/during/after checkpoint publication, rotation, and reclamation; the two-class reclaimable set (the pre-checkpoint snapshot objects and the **non-confirming** publication records; the retired journal frames) with the two-phase idempotent reclamation and the audit ledger; **the confirmed revision records and their consequence-batch objects retained in full, never reclaimed — the RATIFIED v1.8 §5.6 rule, restored per the review's Finding 2** (Revision 1 wrongly allowed their prefix reclamation). **Numerical defaults are PROPOSED engineering judgments grounded in the measured rates** (compact when `summarized_records` would exceed ~2× the active obligation count at a save point; a checkpoint every ~32 publications; a few reference-retention generations) — the workload rates are measured; the thresholds are not, and their sensitivity analysis is a PP-B2/PP-B3 gate (P0-4's no-invention rule, correctly applied).
- **Basis:** [RATIFIED] P0-4 (verify-before-reclaim; the only valid recovery path never deleted; defaults by measurement); [MEASURED] the growth rates (55,127 B per capture-bearing journal transaction; the publication growth 230 KB→3.5 MB at 150→4,800 ticks; ~10.5 ms/revision walk).
- **Alternatives considered:** indefinite retention (rejected — the unbounded chain/journal/snapshot growth); aggressive automatic reclamation (rejected — a reclamation is never automatic at first implementation; PP-B3 delivers it behind an explicit, logged operation).
- **Costs:** the protocol machinery (the eligibility marks, the reclamation ledger, the rotation); the honest communication that total storage is **not strictly bounded** — the confirmed consequence lane is retained in full per the ratified rule, linear at KB-class per consequence: **~52–65 MB per 10-hour fixture-rate session** [EXTRAPOLATED from the measured ~8–10 KB per capture-bearing deactivation × the measured ~55-tick cadence × 360,000 ticks — Revision 1's ~6 MB figure divided by ten and is corrected], comparable in order to the snapshot-cadence term (~15–25 MB/h at a one-per-minute policy).
- **Risks:** a wrong cut breaks a proven recovery guarantee (mitigated: the seven eligibility rules are each traceable to a ratified contract; the two-phase procedure is interruption-safe; the interruption matrices are PP-B3 gates).
- **Evidence needed for approval:** the PP-B3 gates — the interrupted-compaction/reclamation matrices; the long-campaign bounded-storage sweep (the steady state held over an order-of-magnitude duration increase); the recovery-from-checkpoint suites. **Status: OPEN.**

## D-PP-4a — The optional confirmed-evidence reclamation below checkpoints [explicitly a change to a RATIFIED rule]

- **The decision:** whether fully-materialized-and-confirmed consequence evidence (the confirming revision records + their consequence-batch objects) may be reclaimed below checkpoints once a verified anchor's coverage subsumes it.
- **Recommended default: DO NOT APPROVE.** The ratified v1.8 §5.6 retains the confirmed revision records **in full**; Revision 1 of the design wrongly allowed their prefix reclamation, and the architecture review's Finding 2 caught the contradiction. The confirmed lane is the KB-class linear term of §4.3's honest arithmetic (~52–65 MB per 10-hour fixture-rate session) — retained is the default.
- **What approval would require if the owner ever wants it:** the checkpoint anchor carrying a per-key digest of the confirmed set it subsumes; the B3 reconcile's Contract A consulting the anchor's materialized coverage (tier-3 suppression) instead of the chain's per-key records (tier-1) for the reclaimed identities; the explicit acceptance that the audit surface for those identities shrinks to the digest; and the PP-B3 fault-injection matrix extended to the reclaimed-confirmation recovery paths. **This is a change to a ratified retention rule and is presented as such — never as already ratified.**
- **Costs of the default (retention):** the linear-KB confirmed-lane growth, quantified above. **Risks of approval:** the suppression authority shifting from tier 1 (chain inclusion) to tier 3 (materialized coverage) for reclaimed identities — a weaker durable dedup evidence class; the two-contract recovery's confirmed-evidence input shrinking to digests for those identities.
- **Evidence needed for approval:** the owner's explicit decision, plus the extended PP-B3 matrix. **Status: OPEN — recommended default: reject.**

## D-PP-4b — The optional window-scoped idempotency-key uniqueness [explicitly a change to a RATIFIED guarantee]

- **The decision:** whether the chain-wide idempotency-key uniqueness check may be scoped to the retained-plus-recent window after reclamation, with the reclaimed historical keys covered only by digest attestation — bounding the compact reclaimed-key set's linear-lifetime growth.
- **Recommended default: DO NOT APPROVE.** The chain-wide uniqueness is a RATIFIED guarantee (the B2 walk enforcement; the B3 pipeline's dedup anchor — a new record reusing a reclaimed key would collide a canonical effect). The compact index's key component (~40 B per reclaimed record, ~24 KB per 10-hour fixture session — the arithmetic corrected per the review) is part of the honest cost of keeping the guarantee; it is three orders of magnitude below the confirmed lane's own linear term and is quantified in DESIGN §4.2.
- **What approval would require if the owner ever wants it:** the acceptance that a key reuse against a digest-attested historical key becomes detectable only by audit (the digest comparison), not by append-time rejection; the B3 pipeline's dedup scoped accordingly; the PP-B3 matrix extended to the reclaimed-key-reuse paths. **This is a change to a ratified guarantee and is presented as such — never as already ratified.**
- **Costs of the default (retention):** the key component's ~2.4 KB/h growth (part of the index's ~4.8 KB/h). **Risks of approval:** a weakened append-time uniqueness check — a real key collision against reclaimed history would be accepted at append and surface only in audit.
- **Evidence needed for approval:** the owner's explicit decision, plus the extended PP-B3 matrix. **Status: OPEN — recommended default: reject.**

## D-PP-5 — The persistence orchestration (async I/O)

- **The decision:** how the calling-thread costs are removed from the frame path.
- **Recommended default:** the **single-serialization-point I/O orchestration** (DESIGN §5.2, the Finding-4 corrective): **ALL canonical-medium writes route through the one dedicated I/O worker** — the snapshot publications asynchronous, the canonical confirmations synchronous enqueue-and-wait (the authority thread blocks on the worker's committed transaction + the verified read-back, preserving the pipeline's no-false-confirmation contract; FIFO across the single queue covers every canonical write — none occurs outside it). The authority thread performs the T1 journal transactions (the separate file medium; the journal receipt strictly precedes the confirmation's enqueue — the T1-before-T3 contract) and the capture (the bounded post-compaction serialization; the clone-handoff deferred pending release-mode measurements). **The snapshot causal frontier and reject-and-regenerate (DESIGN §5.2, the re-review's Finding-4 corrective):** every capture records its causal frontier (the canonical head at capture, the journal's last committed transaction, the consequential-state coverage the bytes represent); **the admissibility rule: a queued publication is admissible iff the current head is still exactly the capture's head — otherwise the stale snapshot is REJECTED (dropped) and re-captured at the next boundary, never rebased** (a newer parent proves ordering, not containment of earlier confirmed effects; a rebased stale image would become the latest snapshot with a frontier predating confirmations whose journal evidence may have been rotated — exactly the case the accepted regression `recovery_fails_closed_on_confirmed_unmaterialized_without_evidence` proves unrecoverable). The B3 pipeline's stale-parent rebase remains for confirmation batches (per-key evidence, identity-addressed — a ratified mechanism); state images reject-and-regenerate, always; the newest-snapshot frontier never regresses; a rejected publication reports the typed stale result — never "saved". **The backpressure split:** the optional save-point publication (a full queue → the typed busy; the campaign continues; re-publication idempotent) vs the required-durability operations (every confirmation; the graceful close's final publication — the caller waits, FIFO-bounded). Cancellation drops queued-unstarted only; a started transaction runs to completion; the shutdown drains + checkpoints; worker failure = the medium unavailable → fail closed; the worker `Unknown`s reconcile exactly as the synchronous path. **The governing gameplay rule retained verbatim: simulation may continue during pending saves only while verified exclusive authority remains intact, and irreversible actions dependent on unconfirmed progress remain gated.** **No threading is introduced in this phase** — the worker is PP-B4's deliverable behind its own GO.
- **Basis:** [MEASURED] the rig's dev-profile costs (publication 57.750 ms — fits no frame budget; the journal 4.337 + confirmation 7.526 — fit 60 FPS only); [RATIFIED] P0-6 (measure-first synchronous implementation; the I/O-worker ownership boundaries designed — this is that design made concrete).
- **Alternatives considered:** full async (the journal + confirmations too) — rejected: the pipeline's verified-read-back confirmation and the T1 sequencing are ratified synchronous contracts; serialize-then-hand-off with a cloned spine — DEFERRED (the release-mode capture measurements are the trigger).
- **Costs:** one thread + the queue machinery; the completion-reporting surface; the mid-publication kill matrix (PP-B4).
- **Risks:** ordering/backpressure bugs (mitigated: one worker FIFO + the CAS + the idempotency keys; the ordering proofs are PP-B4 gates); the 144/240 FPS story remains gated on the release-mode re-measurement (no stronger claim is made).
- **Evidence needed for approval:** the PP-B4 gates — the mid-publication process-kill matrix; the ordering/monotonicity proofs; the release-mode frame-budget measurements on the rig. **Status: OPEN.**

## D-PP-6 — Migration, backup, and compatibility policy

- **The decision:** the safe path from the existing development saves to the production provider.
- **Recommended default:** the **staged, idempotent migration with a genuine exclusive-authority cutover** (DESIGN §6.1, the Finding-3 corrective): read the old store via its own verified walk (never modified) → content-addressed idempotent inserts → the `ChainSummary`-identical verification → **the seal-first authority transfer under the held source lock** (DESIGN §6.1, the re-review's Finding-1 corrective: acquire the source `HEAD.lock` held across the entire transfer — the per-operation locking blocks every foreign medium operation, and previously opened handles hit the same admission check at their next operation; re-verify the head; **seal the source durably BEFORE anything activates the target** — the `MIGRATED` tombstone written tmp+fsync+rename, with the source-side admission check living in the `LocalFileMedium` open/append path itself; **the fail-closed intermediate** where neither store accepts progression; then the DB authority marker commits in one transaction — the only activating step, strictly after the durable seal; the crash-window table's rows asserted for **process crashes on every platform — and the honestly-marked Windows power-loss row (dual authority possible in-service; prevented only by the offline procedure's archival)**: the cross-medium asymmetry is real (the SQLite activation survives a power loss the file-medium tombstone cannot), so **a genuinely power-loss-safe authority transfer is NOT achievable on Windows from std and is not claimed**; the power-loss-safe path is the **explicitly offline migration** — the campaign closed, the seal-first transfer run, and the source archived out of the standard campaign path (`<root>.migrated-<timestamp>/`) as the OPERATIONAL compatibility boundary; **the older-client admission model**: the tombstone check protects only tombstone-aware clients — existing Stage 5 binaries cannot be stopped by any marker, and for them the archival step + the documented archive-confined divergence consequence are the only protections — the boundary is operational, not merely code-enforced — **constrained to the offline conversion per the Rev-4 re-review** (DESIGN §6.1: an automated, mechanically power-loss-safe authority transfer is NOT achievable under the current primitives — the archive rename shares the file medium's unclaimed Windows power-loss tier — and is NOT claimed; the procedure's exact state machine: the source becomes inaccessible to old binaries at the ARCHIVAL (step 4), and the target becomes eligible for gameplay only after the OPERATOR'S VERIFIED CHECKLIST (step 5 — the gate is the completed checklist, not an automatic state); the power-loss windows' supported recovery: re-run the migration tool — it completes the archival or fails closed on divergence (an old binary's writes confined to the legacy store, never merged; the operator resolves explicitly — forfeit or manually reconcile); the source-reappears recovery: the same re-run; no universal dual-authority-prevention claim where an older executable can still open the legacy store); Rollback: pre-cutover trivial; post-cutover the export path (the DB → a fresh file store via the retained reference writer) or the retained old store until advanced. Downgrade after advancement: **refused, with the export path documented** (never silent). **The quiescent-boundary campaign backup** (DESIGN §6.2, the re-review's Finding-2 corrective): **quiesce** (a boundary with no operation in flight — no journal append, no canonical write, no rotation can interleave) → capture the pair under quiescence (the exact journal copy + `VACUUM INTO`) → the manifest written LAST atomically (binding the DB head H, the journal copy's hash + its last committed transaction, the active journal path, the checkpoint state) — **the pair is coherent by construction; no confirmation can occur between the captures** (Revision 2's online both-orderings claim was falsified by the accepted regression `recovery_fails_closed_on_confirmed_unmaterialized_without_evidence` and is withdrawn); **no manifest = not a valid backup set, refused at restore**; **a backup is labeled usable only after the restored-session recovery verification passes** (the tooling restores the pair in scratch, runs the B4 recovery, asserts the coherent session + the `ChainSummary` parity); interrupted backups are detected and discarded; **the online capture is explicitly DEFERRED — the quiescent capture is the initial protocol**. The original formats remain permanently as independently verifiable references.
- **Costs:** the migration tool + its interruption matrix (PP-B1); the operational backup discipline.
- **Risks:** a partial-migration authority confusion (mitigated: the marker-last rule + the open-time marker check); a live-copied WAL database (mitigated: the checkpoint discipline is documented and tooling-enforced).
- **Evidence needed for approval:** the migration interruption matrix (kills at every stage, old-or-new authority, never partial); the parity suite (D-PP-1's). **Status: OPEN.**

## D-PP-8 — The stage-gated implementation plan

- **The decision:** the sequencing of the (separately authorized) implementation.
- **Recommended default:** **PP-B1 the SQLite medium → PP-B2 the spine compaction → PP-B3 the retention protocol → PP-B4 the orchestration** — dependency-driven (the medium first: everything composes over the seam; compaction second: it bounds what retention and orchestration optimize; retention third; orchestration last so it cannot mask correctness work). Each batch independently testable/reviewable with its own gates (DESIGN §8) and its own GO.
- **Alternatives considered:** compaction first (rejected: the equivalence suites are cleaner over a settled medium); orchestration earlier (rejected: it must not mask correctness work).
- **Costs:** four review cycles.
- **Risks:** none structural — the plan's whole point is independence.
- **Evidence needed for approval:** the owner's GO per batch. **Status: OPEN — no batch is started by the design phase.**
