## 1. The end-to-end session lifecycle (the GO's first item)

`tests/b5_lifecycle.rs`, three regressions over the real 1000-NPC workload:

- **`session_lifecycle_graceful_close_and_restart_matches_the_twin`** — the complete arc: startup, campaign opening (the founding), verified snapshot publication and loading (the chain walk), journal recovery, deterministic continuation, milestone persistence, canonical confirmation, the **graceful close** (the final snapshot + the drop), and the **restart**. The closed-and-restarted durable session ends EXACTLY where the never-persisted legacy twin does (the combined Stage 4 fingerprint, the milestones, the credits; the continuation's captures canonically confirmed).
- **`lifecycle_crash_after_confirmation_restarts_coherently`** — the crash AFTER the canonical confirmation with only the pre-deactivation snapshot on disk: the restart recovers (the confirmed plan re-installs, the confirmation suppresses the replay, the confirmed identities stand InConfirmedChain) and the continuation reaches the twin's state — the **engine fingerprint** (the spine's full logical state: the executions, the follow-up chains, the ledger, the statistics), the milestones, the credits, and both ledger lanes. The presence-derived regions (3/5's empty-scratch deactivations, unjournaled by design) legitimately diverge at the intermediate points — re-derived at the continuation's boundary and re-reactivated by the near-presence run — reaching the twin's final level identically; the divergence and its resolution are asserted, not hidden.
- **`repeated_recovery_is_idempotent`** — the recovery is a pure function of the durable state: recovering twice from the same disk reconstructs the identical session (the combined fingerprint), and the re-drive after the second recovery confirms exactly once.

**The schedule-fidelity corrective the lifecycle test surfaced** (a latent Batch 4 defect, fixed in the same commit `455c817`): the deactivation plan flattened every obligation's schedule to `AtLogicalTime { due }`, but the routine chains self-sustain through **execution-relative** follow-ups (`due = origin + delay`, anchored to actual execution) — so a recovered chain resumed with wrong anchoring semantics (the execution ledger's schedule-kind record diverged; the spine's save was exactly 1,000 bytes shorter — 125 obligations × the 8-byte form difference). The correction: the plan carries the **full schedule form verbatim** — engine-core's `ObligationView` exposes the obligation's exact schedule (additive), `PlanObligation` carries it, and **`deactivation-plan/2`** is the explicitly versioned extension (the schedule discriminant + fields + the due-coherence gate `schedule.due() == due` on restore; v1's flattened form appeared only within B4-review test campaigns — no durable artifact carries one — so the walk reads v2 only, the version bump the documented migration boundary); `plan_events` reconstructs the exact original schedule, so the resumed chains execute with their original anchoring and the ledger's schedule-kind records match the never-crashed path.

## 4. The persistence performance measurement (the GO's fourth item)

**Methodology.** The `--benchmark-persistence` mode (`engine-slice/src/benchmark.rs`, commit `271aa7b`) measures the real workload — 1000 NPCs, 8 regions, the Lod scenario at the accrual peak (150 ticks), budget 200 / near-reserve 60 — as distributions (min/median/p95/max, n per operation): the snapshot serialization (`save_session`, the pure codec cost, n=20); the snapshot publication (the B2 nine-step append incl. its fsyncs, n=20, each publication a distinct session state — the session advances one tick per publication so the chain-unique idempotency key never collides); the T1 journal transaction (the six-phase deactivation's durable composite — the envelope staging, the plan blob, the journal append with its fsync, the post-fsync verify, the in-memory install — n=10 on fresh campaigns, every sample a first transaction on a fresh journal); the canonical confirmation (`commit_canonical`, n=10); the session recovery (`recover`, n=10); and the chain cold-open validation (the B2 founding→HEAD walk at growing chain lengths).

**Pod results (THIS environment — the coder pod, `/tmp` on overlayfs; explicitly NOT authoritative physical-rig evidence):**

| Operation | min | median | p95 | max |
|---|---|---|---|---|
| Snapshot serialization (no I/O) | 2.220 ms | 2.444 ms | 2.951 ms | 3.046 ms |
| Snapshot publication (the B2 append incl. fsync) | 56.3 ms | 152.9 ms | 240.9 ms | 251.9 ms |
| T1 journal transaction (the durable composite) | 8.363 ms | 8.471 ms | 8.710 ms | 8.710 ms |
| Canonical confirmation | 9.181 ms | 9.305 ms | 9.595 ms | 9.595 ms |
| Session recovery | 64.46 ms | 64.60 ms | 65.08 ms | 65.08 ms |
| Chain cold-open (6 / 11 / 21 revisions) | 64.9 / 105.7 / 216.4 ms — **linear, ~10.5 ms per revision** | | | |

**The 60/144/240 FPS interpretation (the review corrective — the calling-thread clarification).** The frame budgets: 16.667 / 6.944 / 4.167 ms per frame. Every persistence operation here is SYNCHRONOUS: **the measured latencies are the calling thread's time costs.** The v1.8 design and the current integration PLACE these operations at simulation boundaries (between ticks; the B4 non-negotiable keeps journal I/O out of the per-NPC hot paths) — but placement is a property of the integration's call sites, **NOT a demonstrated frame-scheduling proof**: whether a host's frame loop is affected depends on the host's threading model, which no Stage 5 delivery demonstrates. The measurements: at the 150-tick workload the journal transaction (8.47 ms median) and the confirmation (9.31 ms) each fit within a 60 FPS frame budget but exceed the 144/240 budgets — a host calling one inside a frame thread would consume half the 60 FPS budget; the publication (152.9 ms median, p95 240.9 ms on overlayfs) and the recovery (64.6 ms) exceed every frame budget outright. **And the boundary costs GROW with campaign duration** (the §5 sweep: the serialization 1.7 ms at 150 ticks → 25.9 ms at 4,800 — past the 60 FPS budget; the projected 10-hour codec ~2 s): a long-session publication on a frame thread would consume many frames. The engine surfaces the costs; the host's scheduling decides. **The overlayfs caveat:** the pod's `/tmp` is the container's overlay union filesystem — its fsync costs are not representative of a native filesystem; the Windows rig's native-NTFS measurements (§7's instructions) remain the authoritative physical evidence, and the B2 record's rig-side measurements remain the accepted durability evidence.

## 5. The storage-growth analysis (the GO's fifth item)

**The review corrective (2026-10-23):** the first version of this section wrongly claimed the spine's execution ledger was bounded by outstanding work. The truth, verified in source and measured below: **the execution ledger, the known/executed indexes, and therefore the serialized snapshot grow with LIFETIME execution history, not outstanding obligations** — `execute_now` appends one `ExecutionRecord` per execution (`ledger: Vec<ExecutionRecord>`), the `known`/`executed` BTreeSets gain one entry per scheduled/executed identity (in-memory RAM; the save derives them from `next_seq` + unfinished on load), and the spine save serializes EVERY execution record in full fidelity. The 150-tick baseline (220,438 B) cannot establish long-campaign boundedness.

**The growth sweep** (the corrected benchmark's measurement across increasing campaign durations, the near-presence fixture):

| Campaign | Executed (the ledger's records) | Scheduled (the known index) | The spine save | The session snapshot | The codec |
|---|---|---|---|---|---|
| 150 ticks | 3,442 | 4,442 | 197,982 B | 220,438 B | 1.7 ms |
| 600 ticks | 13,748 | 14,748 | 517,468 B | 539,924 B | 4.1 ms |
| 1,200 ticks | 27,283 | 28,283 | 937,053 B | 959,509 B | 7.2 ms |
| 2,400 ticks | 54,497 | 55,497 | 1,780,687 B | 1,803,143 B | 13.4 ms |
| 4,800 ticks | 108,984 | 109,984 | 3,469,784 B | 3,492,240 B | 25.9 ms |

**Derived: ~31.0 B per execution (the ledger's serialized share — the dominant lifetime growth); ~23 executions per tick in this fixture; the codec cost scales linearly (~0.24 µs per record).**

The five §5.6 storage classes, corrected:

1. **Execution history — LIFETIME-GROWING.** The spine's execution ledger grows one record per execution (~31 B serialized); the in-memory `known`/`executed` indexes grow one entry per identity; the T1 journal grows 55,127 B per capture-bearing deactivation transaction. The BOUNDED part is the ACTIVE obligation state (queued/blocked/held — budget-limited by design); the ledger and indexes are HISTORY, never active state.
2. **Active indexes** — the active obligations (the lanes/held/blocked) are bounded by the budget/occupancy and the world arrays by the workload (1000 NPCs); but the serialized snapshot EMBEDS the lifetime history, so the snapshot is NOT bounded.
3. **Snapshots/anchors — LIFETIME-GROWING.** Each snapshot's size grows with the campaign's execution count (the sweep); the store grows per publication by the then-current snapshot size — the 150-tick measurement of ~230 KB per publication is the SHORT-RUN value only (at 4,800 ticks one publication adds ~3.5 MB).
4. **Canonical revision history** — one revision per publication and per confirmation batch; each published revision's content object grows with the history it embeds; the confirmation batches stay small (the per-key evidence).
5. **Validation-walk cost** — the cold open is linear at ~10.5 ms per revision (unchanged); the trusted cursor keeps every append O(1); the recovery's snapshot-restore codec is now measured linear in the execution count (~0.24 µs per record).

**The corrected long-term extrapolation (with uncertainty).** The execution rate is the fixture's near-presence occupancy (~23 executions/tick); a live campaign's rate varies with region occupancy between near zero (all-dormant) and the budget ceiling (~200/tick). At the demo 10 Hz: a 1-hour session runs 36,000 ticks → ~828,000 executions at the fixture rate → ~26 MB of ledger and snapshot (at the budget ceiling: ~7.2M executions → ~223 MB); a 10-hour session at the fixture rate → ~8.3M executions → **~257 MB per snapshot**, each publication re-serializing the whole history (the codec ~2 s at that size), the recovery's restore codec similarly (~2 s) plus the chain walk and the journal scan. **These are extrapolations from the measured linear rates with the occupancy uncertainty stated — NOT guarantees; the constant short-run snapshot size is never presented as a long-term bound.**

## 6. The compaction decision evidence (the GO's sixth item)

**The assessment (corrected by the growth sweep).** The first version understated the growth: the session's OWN snapshot embeds the lifetime execution ledger (~31 B per execution serialized), so the growth is not confined to the chain — every publication re-serializes the whole history, the publication cost grows linearly with campaign duration (the codec 1.7 ms at 150 ticks → 25.9 ms at 4,800 → ~2 s projected at the 10-hour fixture-rate history), and the recovery's restore cost grows with it. The accepted architecture's compaction basis (the v1.8 §5.6 authenticated prefix + the complement-of-unfinished) addresses the CHAIN; **the ledger's lifetime growth inside the session snapshot is a further dimension the follow-up's protocol must address** — the spine save's full-fidelity execution ledger is a B1 wire-format contract (the save's integrity gates hash the full history: the conservation and ledger-count identities), so any truncation is a format-level change requiring its own reviewed design.

**The recommendation stands, now with the explicit measured justification: compaction implementation belongs in a separately reviewed follow-up, not Batch 5.** (1) The GO's restriction — irreversible historical-evidence deletion requires a reviewed retention and verify-before-reclaim protocol, which does not exist; the protocol is itself a design deliverable spanning TWO dimensions (the chain prefix + the session-embedded ledger). (2) The measured urgency, stated honestly: at short campaign durations (≤ a few thousand ticks) the boundary costs stay within frame-scale latencies and the disk footprint is modest; at long durations (the 10-hour fixture-rate extrapolation: ~257 MB snapshots, ~2 s publications) the costs exceed any frame budget and the footprint is substantial — **the follow-up is necessary for long-session production, not merely a disk optimization** — but its design (the retention classes: the actionable-unconfirmed T1 intents until confirmed-or-canceled; the confirmed evidence until materialized in a verified snapshot; the ledger's integrity contracts) must not be rushed inside a verification batch. (3) No retention generations are invented here. The follow-up starts from these requirements with the measured rates — ~31 B per execution, 55,127 B per capture-bearing transaction, the publication growth 230 KB→3.5 MB at 150→4,800 ticks, ~10.5 ms per revision walk — as its evidence base.
