## 1. The integration boundary and the crossing object

The crossing layer is `engine-slice/src/crossing.rs` — `SessionCrossing`, the application-facing composition of the B2 medium, the B3 pipeline, and the real Stage 4 simulation (the Spine + NpcWorld + RegionDirector). Its operations map one-to-one onto the v1.8 session-crossing surface:

| Operation | What it does | Durability surface |
|---|---|---|
| `open(store, journal, campaign)` | Founds (or joins) the campaign store — a standalone-authority founding record on first open — and joins the caller's journal (plain or fault-injected, the failure matrix's seam) in one pipeline | The B2 medium chain + the B3 pipeline seeded from the journal scan |
| `deactivate(spine, director, region, now)` | The six-phase transactional deactivation (§3) | ONE T1 journal transaction per capture-bearing boundary; `Option<CaptureReceipt>` — empty-scratch deactivations journal nothing |
| `activate(spine, director, region, now)` | The durable reactivation (§4) | Nothing new journaled — the live application of already-durable captures |
| `publish_snapshot(spine, director)` | The session snapshot (§6) | ONE B2 revision whose content object is the whole authoritative session |
| `recover(store, journal, campaign)` | The crash recovery (§6) | Read-only over disk; reconstructs spine + director + crossing |
| `commit_canonical()` | The pending T1 re-drive | The B3 canonical confirmation (consequence-batch/2) |
| `key_phase(id)` | The per-key durable status surface | The B3 `KeyPhase` lattice |

The medium's `HEAD.lock` is per-operation (the B2 design), so the crossing keeps only the store directory and opens fresh medium handles for publications and recovery; the journal's sidecar lock IS session-scoped, so a same-process second journal open blocks until the first holder drops — the abort-retry regression exercises this discipline explicitly (`drop(crossing)` before the re-open).

## 3. The six-phase transactional deactivation

`SessionCrossing::deactivate` drives v1.8 §5.5.1/§5.5.2 over the real simulation:

1. **Validate** — a live region; the Dormant target from the caller's presence decision (`RegionDirector::target_level`, the read-only routing input).
2. **Determine** — the read-only `DeactivationPlan::prepare` from `Spine::collect_matching` (engine-core's new read-only preparation query, canonically (due, seq)-ordered) and `gather_region_entries` (the shared extraction the legacy path also routes through). Phases 1–2 cost nothing: a pre-durable abort leaves the pre-transition state intact, and a retry re-derives identical keys because the episode frontier advances only on durable commit.
3. **Persist T1** — ONE journal transaction: the capture envelopes (the AWARD form — uniform `Captured` units over the fresh identity's occurrence span (0, δ]) staged in ConsequenceId-sorted order plus the plan blob, through the B3 pipeline's `stage`/`capture`. An empty-capture deactivation journals nothing (the LOD transition is a pure function of presence — re-derivable post-crash; only the crossings are real-execution history needing durable-before-discard).
4. **Verify** — the receipt is post-fsync by the B3 contract; an ambiguous write is auto-reconciled by reread+verify (the B3 `WriteReconciliation` machinery, unchanged).
5. **Install** — the staged prepare/install bundle: five precondition re-validations (level, episode, obligation presence, ledger-key freshness, scratch-delta) BEFORE any mutation, then the non-fallible installation — `Spine::suspend_ids` for exactly the plan's ids (engine-core's new id-exact batch), the ledger captures, the dormant LOD view, the scratch discard, the deactivated region state. The suspension count is the defensive-failure halt signal (ids not currently queued or blocked are not moved and not counted — never a silent partial install).
6. **Typed failure** — `TransitionError::JournalFailed` (pre-durable: the pre-transition state intact, partial records inert, retry with identical keys) vs `TransitionError::InstallIncompatible` (post-durable: the fail-closed HALT signal — a plan-vs-live incompatibility is a bug, never continue-with-region-unchanged; the durable intent stands in the journal and recovery reconciles it).

**The atomicity contract, proven:** pre-durable failure = intact + retry (`pre_durable_failure_aborts_intact_and_retries_identically` — the CapturesWritten fault → the typed abort → the fingerprint and held set byte-exactly intact → the clean retry with identical keys producing the legacy state); unreconciled post-durable = halt (`install_defensive_failure_is_the_halt_signal` — the gap seam between durability and install, an obligation moved → the halt); never a partial install (the five preconditions precede every mutation and the installation itself is non-fallible); mid-install process termination = recoverable (§9's process-kill regression). The equivalence proof: `durable_deactivation_matches_the_legacy_state` — identical scenario pairs through the legacy `director.apply` far boundary vs the durable crossing produce the EXACT same combined Stage 4 fingerprint; the journal holds one transaction per deactivation and the envelope identities are exactly the ledger's captured keys.

## 4. The durable reactivation

`SessionCrossing::activate` commits the captured consequences to credits as the LIVE APPLICATION of the already-durable captures: the legacy activation's install (labeled reconstruction, resume, reclassify) followed by `mark_applied` — the B3 lattice's `JournaledT1 → AppliedToLivePending` promotion, exactly-once. NOTHING NEW IS JOURNALED: the captures are already durable (the deactivation's transaction) and the captured→credits transfer is re-derivable from the ledger plus the activation. A coherent activation refusal is the LEGACY retry semantics (nothing new journaled, the captures stay pending and actionable, the region safely dormant — never a durable-intent abandonment). Phase-1 halt-worthy incoherences: activate-of-live, checkpoint-absent, ledger-key-unknown.

The full-cycle proof: `durable_reactivation_cycle_matches_the_legacy_state` — accrual → the durable far boundary → one tick → the durable near boundary; the combined Stage 4 fingerprint identical to the legacy cycle at every boundary, the credits exactly equal, the per-key phase `JournaledT1 → AppliedToLivePending` through the cycle, and the journal holds ONLY the award captures (one transaction, the capture-bearing deactivation; the empty-scratch deactivations and the activation journal nothing).

## 5. The structured-key migration (the accepted in-memory layout, P1-7)

The `CaptureLedger` is now `ConsequenceId`-structured in memory — pending `BTreeMap<ConsequenceId, u64>` + applied `BTreeSet<ConsequenceId>`, the capture/status/apply interface taking structured identities, the director's call sites constructing them via `crossing_id(region, episode, npc)` — while the fingerprint's wire form remains the packed Stage 4 encoding: `pack_stage4` IS the legacy `consequence_key` expression (the bijection the engine-persist boundary trio pinned, proven LIVE against this crate's authoritative layout by `structured_keys_are_the_stage4_packed_layout` — pack == consequence_key, the unpack round-trip, injectivity over the region/npc/episode boundary sweep). The structured (region, episode, npc) field order coincides with the packed numeric order (field-aligned bit packing), so `capture-ledger/2` keeps byte-identical output — no /3 storage-encoding change is needed because the packed form already IS the structured key's canonical packed form. `consequence_key` remains as the layout documentation and the compatibility oracle.

## 6. The session snapshot and the crash recovery

**The snapshot** (`publish_snapshot`): ONE content object, `engine-slice/session-snapshot/1`, carrying the complete authoritative session — the spine save with the world section (npc-world-save/1) plus the director state (region-director-save/1, including the structured-keyed capture ledger and the materialization evidence) — published atomically through the B2 medium's nine-step append. Discovery (`latest_snapshot`) walks the chain from HEAD back through the parents; the first content object that restores as a session is the latest snapshot.

**The recovery** (`SessionCrossing::recover`), the composition in order:
1. **The snapshot restore** — spine + director from the latest chain snapshot.
2. **The crossing restore** — the post-snapshot crossings the journal's captures claim (the capture delta minus the snapshot's scratch per identity), restored exactly as they were at the deactivation via `NpcWorld::apply_recovered_crossings`, so the staged install's scratch re-validation matches.
3. **The plan-based three-case** (§5.5.2): per committed transaction with a non-empty plan blob, restore the DeactivationPlan and compare its episode against the recovered director's episode for that region — greater = pre-state → `install_recovered_deactivation` (the id-exact held reconstruction: the snapshot's stale chains removed, the plan's obligations inserted as held under their OWN identities, the scheduled statistic adjusted by the replacement delta — the conservation holds); already-installed = skip (the post-state never a duplicate).
4. **The B3 reconcile coherence verification** (`build_anchor`): per journal identity the pipeline counters — pending in Captured, applied in Credits — with the coverage (0, δ]; every journal envelope must be suppressed by the anchor's coverage (a reapplied envelope is recovery-double-application — the halt). The exact canonical effect provenance (consequence-batch/2's per-entry effect commitments) flows through unchanged.
5. **The re-opened crossing** — the pending T1 re-drive available via `commit_canonical`.

Regressions: `recovery_reinstalls_the_deactivation_after_a_crash` (THE W2 window honestly simulated: the snapshot at the accrual peak, the durable deactivation, the in-memory state lost — the checkpoint, the ledger, the sentinels, and the milestones match the lost state exactly; the empty-scratch deactivations stay presence-re-derivable; the re-drive confirms InConfirmedChain); `recovery_from_an_older_anchor_restores_post_snapshot_crossings` (the older anchor: the snapshot at tick 50 before the crossings, the accrual to 150, the crash — the post-snapshot crossings restored through the capture delta, the plan installed through the held reconstruction, the milestones match the lost state's exactly).

## 7. The real milestone correctness (the awarded-threshold eligibility guard)

`MILESTONE_PERIOD = 16` with the awarded-threshold eligibility: a crossing at the period boundary awards only when its threshold index exceeds the awarded count (`steps / 16 > milestones[npc]`) — behavior-identical on the live paths (every 16th step awards exactly one; the frozen baselines pin it), recovery-correct (a restored world holds recovered milestones without the matching rewound steps, so resumed executions never re-award). Conservation: the plan's captured deltas sum exactly to the ledger's pending total (`prepared_plan_matches_the_legacy_deactivation`); identity-safe restoration: the recovered milestones are the crossings the snapshot predates, applied through `apply_recovered_crossings` — never a double count with the snapshot's own.

## 8. The two demonstrations (GO items 7–8)

**The encounter rollback policy against real simulation state** (`encounter_rollback_policy_against_real_simulation_state`): an encounter over a region-4 NPC's live consequential state (the counters read from the world at the accrual peak — real crossed milestones, the pending lane fed at execution), two provisional-recorded occurrences with one promoted durable mid-encounter, THE FAILURE — the rollback: the durable promotion SURVIVES with its counter and its lane signal (conservation holds), the provisional effect rolls back (eligibility restored), the promoted occurrence never returns to the provisional lane; the legitimate re-attempt: the discarded occurrence is earnable again, the durable-covered occurrence is never a second award (the idempotent no-op). The gameplay policy (which effects are durable) stayed outside the machinery throughout.

**The irreversible-operation gate on canonical confirmation** (`irreversible_operations_gate_on_canonical_confirmation`): `key_phase` distinguishes every phase and the gate opens ONLY on InConfirmedChain — unknown never permits; the journaled capture (pending T1) stays gated (never conflated with confirmation); the live application (AppliedToLivePending — live effects exist, the canonical confirmation does not) stays gated; the canonical confirmation opens the gate. The engine surfaces the phase; the gameplay decides.

## 11. Known limitations

1. **Windows `SyncTier::ProcessCrashOnly`** — preserved unchanged from B2/B3: the custom std provider is qualified for the process-crash tier only on Windows; OS-crash/power-loss acknowledged-revision persistence is not claimed; the production provider selection remains the lead's (SQLite the identified fallback, never added).
2. **Single-writer crossing per journal** — the journal's sidecar lock is session-scoped; a same-process second open blocks until the first holder drops (the abort-retry regression's documented discipline). Cross-process composition of the crossing itself (vs the pipeline's foreign-confirmation path) is deferred.
3. **No compaction or retention** — the journal and the snapshot chain grow unboundedly; explicitly out of B4 scope, deferred to a later authorized batch.
4. **Linear snapshot discovery** — the HEAD-back chain walk reads each record and tries the restore; no snapshot index exists.
5. **Empty-scratch deactivations journal nothing** (by design — presence-re-derivable): a crash between an empty-scratch deactivation and the next snapshot leaves that LOD transition to the director's presence-driven re-derivation; no durability claim is made on it.
6. **No crossing-level cancellation of a durable deactivation intent** — v1.8's six phases do not define an un-install; the pipeline-level `cancel_transaction` remains available for T1 intents pre-confirmation, and supersession at the crossing is the episode frontier. An explicit crossing-level cancel API would be new scope.
7. **The recovery trusts the pair** — the campaign store + journal must be from the same campaign; a divergent pair fails closed through the reconcile (never a guess).
8. **The process-kill harness bounds at 120 s** with kill-on-expiry — a runaway child is killed, never hung (the harness discipline; the observed runtime is ~0.2 s).
